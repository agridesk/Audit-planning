AMS-01.6 — AUDIT PLANNING DECOMPOSITION AND TARGET DATA MODEL

Date: 2026-09-20
Status: Architecture draft based on dev commit 99ea6ad
Scope: Audit planning, lifecycle ownership, reader/writer dependencies, target Model C and migration

1. FIXED ARCHITECTURE

Target chain:

Company -> Company Scope / Certificate Lifecycle -> Audit Obligation -> Audit Visit <-> Auditor Availability

An Audit Visit can cover multiple Audit Obligations. Audit ID remains the canonical operational key for the physical visit. Availability remains linked to Audit ID. Company Scope ID and Obligation ID are new stable keys. No one-Audit-ID-per-scope model is introduced.

4. TARGET PHYSICAL TABLES

4.1 Company_Scopes

Canonical purpose: durable Company x Scope relationship and certificate lifecycle configuration.

Required fields:
- Company_Scope_ID
- Company_UID
- ScopeCode
- Active
- Lifecycle_Type
- Certificate_Birthday
- Company_Formal_Hours_Override
- Certificate_Metadata_JSON
- Created_At
- Updated_At

Rules:
- Unique active relationship on Company_UID + ScopeCode.
- Certificate_Birthday is null for lifecycle types without certificates.
- Company_Formal_Hours_Override is optional and persists across cycles.
- Planning duration is not stored here.

4.2 Audit_Obligations

Canonical purpose: what must be audited for one scope in one cycle or externally triggered period.

Required fields:
- Obligation_ID
- Company_Scope_ID
- Company_UID
- ScopeCode
- Cycle_Key
- Trigger_Source
- Obligation_State
- Base_Expiry_Date
- Extension_Applied
- Extension_Metadata_JSON
- Effective_Expiry_Date
- Planning_Window_From
- Planning_Window_To
- Formal_Hours
- Preassigned_Auditor_Email
- Allow_Self_Planning
- Created_At
- Updated_At
- Closed_At

Rules:
- Formal_Hours is the resolved cycle value. It is seeded from Company_Scopes.Company_Formal_Hours_Override, otherwise Config_Scopes.Formal_hours. This preserves the hours used for a specific obligation even if a later default changes.
- Planning_Duration remains canonical only in Config_Scopes. Planning read models resolve it by ScopeCode; it is not copied into Company_Scopes or Audit_Obligations. Actual reserved time remains in Visit.Planning_JSON. There is no company-level planning-duration override.
- Certificate lifecycle fields are null for MPS-ABC.
- MPS-ABC Cycle_Key is the calendar/import year and Trigger_Source is ECAS.
- Preassignment and self-planning permission exist before a Visit and therefore belong here.

4.3 Audit_Visits

Canonical purpose: physical/operational planning and workflow unit.

Required fields:
- Audit_ID
- Company_UID
- Visit_Location_ID
- Visit_Location_Snapshot_JSON
- Assigned_Auditor_Email
- Status
- Planning_JSON
- Date_Planned_Index
- Date_Approved
- Status_Since
- Last_Manager_Decision
- Last_Manager_Decision_At
- Manager_Comment_Last
- Last_Auditor_Decision
- Last_Auditor_Decision_At
- Auditor_Comment_Last
- Created_At
- Updated_At

Rules:
- Planning_JSON remains the planning truth.
- Date_Planned_Index is a derived/materialized index of the first planned block, not a competing truth.
- Company_UID is retained on VI for integrity and hot-path filtering.
- Availability writes always use Audit_ID.

4.4 Audit_Visit_Obligations

Canonical purpose: link one physical visit to one or more obligations.

Required fields:
- Audit_ID
- Obligation_ID
- Link_State
- Linked_At
- Unlinked_At

Rules:
- Composite key Audit_ID + Obligation_ID.
- An open obligation may have at most one active visit link.
- A visit must link only obligations for the same Company_UID.
- The link table is canonical; no second canonical Obligation_ID list is stored in Audit_Visits.
- Cached maps may provide Audit_ID -> obligations and Obligation_ID -> active Audit_ID.

4.5 Config_Scopes additions

Rename/extend semantic ownership:
- Default_hours -> Formal_hours
- Scheduling_hours -> Planning_duration
- Lifecycle_Type
- Obligation_Trigger_Type

Do not encode multi-scope relationships as repeated columns. Add a separate Config_Scope_Dependencies table:
- Dependency_ID
- Parent_ScopeCode
- Child_ScopeCode
- Relationship_Type
- Must_Audit_Together
- Share_Expiry
- Active

For GAP/GRASP, GRASP is the dependent/add-on scope. The dependency determines shared expiry and bundling; no generic overlap fallback may override it.

4.6 Exact identifiers

- Company_UID: retain the existing UUID unchanged.
- Company_Scope_ID: CS_<UUID without hyphens>.
- Obligation_ID: OBL_<UUID without hyphens>.
- Audit_ID: retain every existing Audit ID unchanged; new visits continue to use the established AUD_ prefix until a separate ID migration is approved.
- Dependency_ID: DEP_<UUID without hyphens>.

IDs are opaque. Business meaning, year, company name and row number must not be parsed from them. Backfill is idempotent through unique natural-key checks, not by regenerating identifiers.

Natural uniqueness:
- Company_Scopes: Company_UID + ScopeCode.
- Audit_Obligations: Company_Scope_ID + Cycle_Key + Trigger_Source, with an explicit sequence only when the business permits multiple obligations for the same cycle.
- Audit_Visit_Obligations: Audit_ID + Obligation_ID.

5. SELF-PLANNING AGGREGATION RULE

When multiple obligations are bundled into one visit, self planning is allowed only when:
- all linked obligations allow self planning;
- all have the same preassigned auditor;
- that auditor is qualified for every linked scope;
- all hard constraints pass.

This is a safe derived Visit capability, not a separately editable Visit field.

6. PLANNING WINDOW AND BUNDLING

- Every obligation owns its own validated planning window.
- A visit may link multiple obligations only when their dependency rules allow bundling and one visit schedule satisfies every linked obligation window.
- For ordinary compatible obligations, the feasible visit window is the intersection.
- Empty intersection means the obligations cannot be bundled in that visit. There is no union fallback.
- Dependency policies may define shared lifecycle/expiry behavior, but may not silently broaden a hard window.

7. COMPLETION TRANSACTION

Required order under one orchestration lock:
1. Re-read Visit, active links and obligations.
2. Validate Visit is Accepted and linked obligations are closable.
3. Append one realized physical Visit event using the existing Audit ID.
4. Persist realized scope/obligation linkage for history.
5. Mark each linked obligation completed.
6. Apply lifecycle policy separately per obligation.
7. Create successor obligations only where the policy requires it.
8. Never auto-create a successor for MPS-ABC.
9. Release Availability by Audit ID.
10. Remove/close the active Visit and links.
11. Commit invalidation generations and post-commit notifications.

Failure before the commit point restores all staged writes. Notification failure after commit never rolls back the transaction.

8. PERFORMANCE READ MODEL

Do not join three full sheets on each planner call.

Build compact generation-keyed catalogs:
- CompanyScopeCatalog: Company_Scope_ID keyed records and Company_UID -> scope IDs.
- ObligationPlanningCatalog: only open/plannable obligations with resolved scope, hours, window, preassignment and dependency group.
- VisitCatalog: active visits keyed by Audit_ID.
- VisitObligationLinkCatalog: Audit_ID <-> Obligation_ID maps.
- PlanningCandidateProjection: compact records used by Batch, Workspace and Year Planning.

Rules:
- Load each source table once per generation, never once per candidate.
- Use targeted ID lookup for single-audit actions.
- Invalidate by affected Company_UID, Obligation_ID and Audit_ID where possible.
- Compatibility fields in Audit planning are projections and never accepted as authoritative input after their ownership switch.
- Cache is disposable and never owns lifecycle or planning truth.

9. MIGRATION PHASES

Phase 0 — Contract and diagnostics
- Freeze the column ownership matrix and target schemas.
- Add schema validators and duplicate/orphan diagnostics.
- Add tests that prove existing operational behavior before ownership changes.

Phase 1 — New persistence and backfill, no ownership switch
- Create Company_Scopes, Audit_Obligations, Audit_Visit_Obligations and Config_Scope_Dependencies.
- Backfill CS and OB from existing Audit planning rows.
- Create one VI relationship for every current active Audit ID.
- Exclude fake ABC birthday/expiry from canonical certificate fields.
- Run read-only comparison reports; legacy Audit planning remains owner during this phase.
- Persist a migration batch ID and source Audit ID on every backfilled record so a failed batch can be removed without touching pre-existing records.

Phase 2 — Scope/lifecycle owner switch
- Move Scope Manager writes to CS/OB.
- Move ECAS creation/mutation to ABC obligations.
- Move extension and planning-window writes to OB.
- Replace AnnualCycle Visit cloning with per-obligation successor creation.
- Generate the legacy C:V, Y:Z, AH and AS:AT fields only through one compatibility projector.
- Block direct production writes to migrated lifecycle columns.
- Switch one ownership domain only after its writer inventory is green; do not leave both old and new public writers active.

Phase 3 — Visit-link integration
- Make new planning create/update VI and active LK records from selected obligations.
- Keep Audit planning as the physical VI table during this phase.
- Batch, Workspace and self-planning consume ObligationPlanningCatalog and write through the same atomic Visit planner.

Phase 4 — Completion/history conversion
- Convert Completion to close linked obligations independently.
- Add realized obligation/scope linkage while retaining one realized Visit per Audit ID.
- Retire AnnualCycleEngine row-copy behavior.

Phase 5 — Reader migration and hot-path projection
- Move planning demand, eligibility, notifications, rotation inputs, Year Planning and Cockpit to compact catalogs.
- Remove full-sheet runtime joins and legacy slot dependence.
- Prove cache invalidation and cold-path bounds.

Phase 6 — Legacy column retirement
- Remove migrated lifecycle/scope columns from Audit planning only after no production writer or reader depends on them.
- Retain VI operational columns and Audit ID.
- Preserve historical Audit IDs without re-keying.

10. REQUIRED MIGRATION GATES

- Every current Audit ID maps to exactly one VI.
- Every active scope flag maps to exactly one obligation.
- Every active Visit has at least one active obligation link.
- No open obligation has more than one active Visit link.
- Company_UID agrees across CS, OB, VI and LK joins.
- Formal-hours totals reconcile with current S for all migrated rows.
- Planning-duration totals are resolved from Config_Scopes and reconcile with Visit Planning_JSON where a visit already exists.
- No ABC obligation has a canonical certificate birthday or expiry.
- GAP/GRASP dependency tests cover shared expiry and must-audit-together behavior.
- Existing Availability records still resolve solely by Audit ID.
- Completion produces one realized Visit record and closes all linked obligations exactly once.
- Cold planner load uses bounded table reads and no per-row sheet calls.

11. VERIFIED HIGH-RISK CURRENT DEPENDENCIES

- AnnualCycleEngineV5.js copies a full Audit planning row to create a successor and therefore mixes Visit, lifecycle, scopes, hours, preassignment and windows.
- AuditManagerToolsScopes.js creates or rewrites the current row and stores company-specific scope hours on the Visit row.
- ECAS_AnnualValidation.js writes scope flags/hours and creates ABC rows directly in Audit planning, including the fake 31-12 birthday workaround.
- CoreStatusMachine.js and ManagerPlanningBackend_CORE_SPLIT.js own operational planning/status writes and clear visit fields during reopen.
- CompletionService.js relies on the current Audit planning row, appends realized history, invokes recurring lifecycle behavior, releases Availability and deletes the active row.
- RejectedAuditsV5.js archives a projection of the active Visit and deletes the active row.
- BatchPlanningCandidateEngine.js, PlanningDemandService.js, AuditorV5Backend.js, ManagerPlanningBackend_CORE_SPLIT.js and notification renderers consume broad Audit planning projections.
- AuditPlanningPerfCache.js, AuditPlanningRowIndexCache.js and persisted planning caches assume Audit planning is the hot-path aggregate.

12. IMPLEMENTATION BOUNDARY

No production implementation starts until:
- this decomposition is accepted;
- exact sheet headers and ID formats are fixed;
- migration/backfill rollback behavior is specified;
- current status-machine debt remains explicitly outside the lifecycle migration.

14. ROLLBACK CONTRACT BY PHASE

- Phase 1 rollback: delete only rows carrying the migration batch ID. No current operational sheet changes.
- Phase 2 rollback before ownership cutover: discard new-domain writes and rebuild from legacy.
- Phase 2 rollback after ownership cutover: stop traffic, restore the last pre-cutover export, and replay the bounded new-owner change log through the compatibility projector. Never reverse by accepting edited legacy projection cells as truth.
- Phase 3 and later: every mutation service must stage before-images for CS, OB, VI, LK and Availability records touched by one command. Restore only those explicit records on pre-commit failure.
- Post-commit notification failures are retryable queue failures and never trigger data rollback.
