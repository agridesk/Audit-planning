21.3 Dynamic scope capacity
- Config_Scopes remains canonical.
- Initial supported design boundary: 20 active scopes.
- Scope handling must be dynamic within that boundary; adding/activating a configured scope must not require scope-specific code changes.
- Remove fixed positional scope assumptions from UI, qualification, notifications, exports, calendar, persistence and tests.
- Company Scope / Audit Obligation remain lifecycle owners under Model C.

21.4 Rotation — canonical threshold policy
Config_Scopes owns the applicable rotation maximum per scope.
- current count <= configured maximum: allowed;
- configured maximum + 1: warning/exception path; planning is only permitted with explicit permission context and must remain visible/auditable;
- configured maximum + 2 or more: HARD BLOCK; planning is not possible.
No UI may silently weaken this policy. Canonical rotation validation remains the owner.

21.5 Self-planning and acceptance
- Manager-planned audit: Pending Planning -> Plan -> Approved; Auditor Accept -> Accepted.
- Auditor self-planning: Pending Planning -> Plan -> Pending Approval; Manager Approve -> Accepted directly. The auditor does not perform a redundant second Accept after submitting the self-planning.
- For a manager-planned Approved audit, Manager may Accept on behalf of the assigned Auditor when the Auditor has confirmed outside the system.
- Every Accepted transition records the actual actor. Manager-on-behalf acceptance additionally records the auditor on whose behalf acceptance occurred, source and reason/context. Acceptance provenance is auditable.

21.6 Controlled Re-adjust — materiality rule
Re-adjust remains an action/mode through Workspace -> Preflight -> canonical writer.
- Change of audit day/date: material -> return to Pending Planning and restart normal planning flow.
- Change of scope(s) affecting the current planned visit/audit: material -> return to Pending Planning and restart normal planning flow.
- Scope/certificate lifecycle changes that affect only future certification cycles/obligations and do not change the current planned visit are not a reason to reset the current audit status.
- Time change within the same audit day (for example 08:00-16:00 to 09:00-17:00): preserves the current lifecycle status, including Accepted, provided canonical Availability/conflict/planning-window validation passes. No renewed auditor acceptance is required solely for this same-day time change.
- When an Accepted audit keeps its status after such a manager-made same-day time change, the Auditor Portal must show a small, non-blocking warning/tooltip on that audit indicating that the manager changed the audit time. The signal remains visible until the auditor has seen/acknowledged the change; it is informational and does not introduce a new lifecycle status or acceptance step.
- Other non-material changes may preserve status when they do not change the audit day or scope set and pass the relevant canonical validators.
- Change of execution location while audit day/date, assigned auditor and scope set remain unchanged may preserve Approved/Accepted status, provided canonical Availability, travel/conflict and planning-validity checks pass. Execution-location change is not by itself a lifecycle reset trigger.
- Change of assigned auditor while date/day, scopes and planned time structure remain unchanged preserves the planning itself. The new auditor must explicitly accept the assignment before the audit can be Accepted; an already Accepted audit therefore returns to Approved for re-acceptance by the new auditor. Before reassignment is committed, canonical qualification, rotation, Availability, same-day capacity/overlap, travel/conflict and planning-validity checks must rerun for the replacement auditor; hard failures block reassignment.

- If a company/scope formal-hours change makes an already Approved/Accepted Visit under-planned, preserve the current lifecycle status. Surface a hard planning-validity warning/block until planned hours are corrected; do not silently reset lifecycle status. The audit cannot progress through planning-dependent downstream completion while this hard inconsistency remains.
- Completed remains immutable for operational Re-adjust.
This rule supersedes older generic wording that every time/hours/block change automatically resets lifecycle status.

21.7 3S performance — all user-facing mutation paths
Speed is a release criterion for every migrated/new 2.0 capability, not a later polishing phase.
Required hot mutations include at minimum:
- add/change/deactivate company audit scope and resulting hours recalculation;
- lifecycle/status transition;
- planning Save / Modify / Re-adjust / Cancel;
- extension apply/undo and resulting effective expiry/planning-window projection;
- company/planning-profile updates that affect planner decisions.
Targets:
- local UI response immediate where no server decision is required;
- common cached/read-model interaction < 1 s target;
- major decision-ready load approx. <= 2 s p95 where technically realistic;
- no normal mutation may trigger repeated multi-second full-sheet scans or broad rebuilds.
Required strategy: targeted/indexed reads and writes, compact read models, deterministic targeted invalidation, optimistic UI only where canonical response can safely reconcile, and no synchronous non-critical work that unnecessarily blocks the user response. Correctness/transactional invariants remain mandatory.
Performance acceptance evidence is required per migrated capability; functional parity alone is not sufficient.

21.8 Extension interaction
Extension apply/undo is a Model C obligation/cycle mutation, not Visit lifecycle truth. It must update effective expiry/planning-window projections through the canonical owner, invalidate only affected read models/caches, and return a refreshed decision result without a broad full-grid rebuild. Extension interaction is explicitly a 3S hot path.

For every surface, migration evidence must state: existing UI entry point, canonical backend/SSoT owner, 2.0 entry point, functional acceptance, 3S/performance acceptance and legacy-retirement status. Missing UI exposure is not permission to duplicate the backend.

21.11 Existing implementation evidence is reusable
Existing accepted components/tests are migration assets, including Model C Scope ownership, extension service, canonical planning modify/Re-adjust foundation, Planning Workspace, Availability, company update dialog/proposal flow, Manager Tools, maps and lifecycle services. Planning 2.0 must consume or adapt these owners. A new UI does not reset completed backend work.

21.12 Scope/cycle mutation status isolation
- Current Visit lifecycle status changes only when the mutation materially changes that current planned Visit.
- Adding/removing/changing a scope linked to the current planned Visit is material and follows 21.6.
- Company Scope / certificate changes that only affect future certification cycles or future obligations do not reset the current Visit status.
- Extension apply/undo is obligation/cycle-specific and does not by itself reset a current Visit status unless it materially changes that Visit's canonical planning validity; any resulting invalidity is handled explicitly by canonical validation, never by an implicit blanket status reset.
- Historical scope/certificate truth is never destructively deleted.


21.13 Company data and preferred-period mutation isolation
- Companies remains canonical company truth; Locations_JSON remains the sole canonical location owner.
- Auditor-originated company-data/preferred-period changes remain proposals until manager review/acceptance; they do not directly mutate Companies.
- Preferred audit months/period are planning guidance for future planning and do not by themselves alter the lifecycle status or committed Planning JSON of an already planned Visit.
- General company/contact/comment/constraint updates do not reset an active Visit merely because company master data changed. If a changed canonical field materially affects the current Visit (for example its selected execution location or another planning validator input), the current Visit is explicitly revalidated under 21.6 rather than blanket-reset.
- Accepted proposal application must use targeted cache/read-model invalidation and audit trail; no duplicate company truth and no broad rebuild.

21.14 Re-adjust confirmation and notification semantics
- A lifecycle-preserving Re-adjust must still create an audit-trail event containing actor, timestamp, changed fields and before/after values or equivalent deterministic change metadata.
- Material changes that require renewed approval/acceptance use the canonical lifecycle notification for the resulting state; informational changes that preserve status must not manufacture a lifecycle transition.
- Manager-made same-day time changes on Accepted audits use the informational auditor signal defined in 21.6. Similar informational signals may be used for other lifecycle-preserving changes only where operationally useful; they remain separate from status.
- Notification delivery failure never rolls back an otherwise valid canonical mutation; Notification Queue remains the delivery SSoT.


21.15 Company master-data parity and ownership
- Manager 2.0 must retain the existing Companies operational surface: list/search, create company, edit company, status, country/time zone, contacts, communication language, region, comments, planning preferences and Locations_JSON-backed locations.
- Manager company creation/editing writes through the existing canonical Companies backend; 2.0 must not introduce a second company store or duplicate write path.
- Auditor company adjustments remain proposal-only. Company_Update_Proposals is the staging/review path; manager review accepts/rejects and accepted changes are applied to Companies with audit trail.
- Preferred audit months and less-suitable weekdays/hours remain planning preferences/soft constraints, not hard planning blocks. Changes do not rewrite existing Planning JSON or lifecycle status by themselves.
- New companies must become available to Scope Manager / Model C ownership without manual cache repair; targeted invalidation/read-model refresh is part of acceptance.

21.16 Hard planning validity versus manager discretion
- Canonical hard planning failures remain non-overridable by ordinary Manager/Auditor UI actions: double booking/overlap, explicit hard auditor unavailability, outside canonical planning window, invalid qualification/dependency, and other validator-defined hard failures. Recurring/default soft unavailability follows 21.46 and remains overrideable through the governed warning path.
- Manager discretion applies only to explicitly classified soft warnings/preferences. A UI acknowledgement may record the decision but may not convert a hard failure into a valid canonical plan.
- Weekend handling, travel burden, sustainability preference, company less-suitable days/hours and rotation pressure remain governed by their explicit rule classifications; rotation specifically follows 21.4.
- Planning 2.0 must render hard versus soft outcomes distinctly and reuse one canonical validator owner for Manager, Auditor, Re-adjust and later batch/bulk planning.


21.17 Archive/history and operational export parity
- Rejected remains terminal lifecycle history. 2.0 does not introduce a normal restore/reopen transition.
- Completed remains lifecycle-immutable operational history in Log realized audits. Controlled realized administrative corrections are permitted only through the governed process in 21.49 and are not Re-adjust.
- Manager 2.0 exposes completed and rejected history through bounded/paged reads rather than hydrating archives on first paint.
- Auditor 2.0 preserves the existing selected-audit export capability, including Excel and PDF, through the existing backend contract or a compatible canonical successor.
- Export generation is not a first-paint dependency and remains outside portal hot paths.


21.18 Completion parity and provenance
- Completion remains a canonical lifecycle action from Accepted to Completed and uses CompletionService / StatusMachine ownership, never a direct UI archive write.
- Auditor completion records the actual auditor actor. Manager completion on behalf of the auditor remains supported and must preserve truthful provenance, including manager actor and on-behalf mode/reason where required by the canonical completion contract.
- Completion must preserve transactional ordering across validation, realized-audit history, recurring-cycle handling, Availability release and active-row retirement; partial completion is not an acceptable success state.
- Completion UI and history/export surfaces in 2.0 must reuse this owner rather than rebuilding completion logic.


21.19 Company deactivation with open audits
- Changing a Company to Inactive while it still has open Approved/Accepted audits does not silently invalidate, complete, cancel or archive those audits.
- Those open audits enter a hard operational hold: they cannot progress until a Manager makes an explicit decision for each affected audit or governed group of audits.
- The hold must be visible in Manager 2.0 and, where relevant, Auditor 2.0, with the Company inactive condition and affected Audit ID(s) clearly identified.
- Company deactivation also blocks creation of new audits/cycles for that Company while Inactive.
- Resolution must use an existing canonical lifecycle/planning action where applicable; no hidden status rewrite and no new pseudo-status solely for this hold.
- Deactivation and resolution decisions require audit trail and targeted cache/read-model invalidation.


21.20 Auditor deactivation with assigned open audits
- Deactivating an Auditor does not automatically rewrite lifecycle status for already assigned Approved/Accepted audits.
- Every affected open audit enters a hard operational hold until a Manager explicitly reassigns it; while held it cannot progress operationally under the inactive auditor.
- Reassignment then follows 21.6: existing planning is preserved when date/day, scopes and planned time structure are unchanged; all canonical replacement-auditor validations must pass; the new auditor must explicitly Accept before the audit can be Accepted.
- For an audit that was Accepted before the reassignment, the reassignment itself returns it to Approved for the new auditor's acceptance. The deactivation event alone does not perform that transition.
- The hold and affected Audit IDs must be visible to the Manager; no pseudo-status is introduced solely for the hold.
- Auditor deactivation, hold creation and reassignment require truthful audit trail and targeted invalidation.


21.21 Loss of auditor qualification after planning
- If an assigned Auditor is no longer canonically qualified for any required scope of an Approved/Accepted audit before execution, the audit returns to Pending Planning.
- This is a hard planning-validity failure, not an operational hold and not a soft warning.
- Existing planning may remain available as historical/replanning context, but it is no longer a valid committed plan and cannot preserve Approved/Accepted lifecycle state.
- Replanning must rerun qualification, rotation, Availability, overlap/capacity, travel/conflict, planning-window and other canonical validators before the audit can progress again.
- The qualification-loss transition requires audit trail, appropriate lifecycle notification and targeted invalidation.


21.22 Extension action stage boundary
- Apply Extension and Undo Extension are available only while the audit is in Pending Planning / planning stage.
- Once an audit has progressed to Pending Approval, Approved or Accepted, Apply/Undo Extension is not an available operational action.
- Therefore extension apply/undo cannot create an Approved/Accepted audit outside a restored planning window; roadmap and acceptance tests must not model that impossible transition.
- Extension mutation remains a pre-commit planning/cycle action and must be validated before the audit leaves Pending Planning.


21.23 Pending Approval is a review boundary
- Pending Approval represents an Auditor-submitted plan awaiting Manager review; it is not an Extension editing stage.
- Manager approval of Auditor self-planning follows the self-planning lifecycle rule in 21.5. The implementation must be migrated from the older generic Pending Approval -> Approved contract to the canonical direct-accept outcome defined there.
- If the Manager does not accept the submitted planning, the audit returns to Pending Planning through the canonical return/cancel/deny successor action; planning corrections are made there rather than silently editing an Auditor submission while approval remains pending.
- Approval/rejection review must show the submitted planning context needed for an informed decision without rebuilding Planning JSON client-side.


21.24 Multi-location planning parity
- Multi-location companies/audits are first-class planning input. One audit may require HQ plus one or more active secondary sites/stops.
- Companies.Locations_JSON remains the only authoritative location set; legacy Location, GPS-data and Locations_to_plan remain derived mirrors and may not determine visit truth independently.
- Planning JSON must retain the actual location per planned block/segment where multiple locations are involved; travel/conflict validation must use those actual visit locations rather than assuming HQ.
- Planning 2.0 must support the existing multi-day/non-consecutive/segmented planning model together with multi-location selection without introducing a second visit model.
- Future trip/workweek routing consumes these committed visit locations; it does not rewrite them as routing truth.


21.25 Deactivation of a planned execution location
- If a location in Companies.Locations_JSON is deactivated while an Approved/Accepted audit is committed to that location, lifecycle status is not automatically rewritten.
- The affected audit enters a hard operational hold and cannot progress until a Manager selects a valid active execution location.
- Selecting the replacement location follows the execution-location rule in 21.6: lifecycle status may remain when canonical Availability, travel/conflict and planning-validity checks pass.
- The hold must be visible to Manager and relevant Auditor views; no pseudo-status is introduced.
- Location deactivation, hold and resolution require truthful audit trail and targeted invalidation.


21.26 System-wide scope deactivation with open audits
- Deactivating a scope in Config_Scopes does not automatically rewrite lifecycle status for existing Approved/Accepted audits that contain that scope.
- Every affected open audit enters a hard operational hold and cannot progress until a Manager explicitly decides how that audit is to be handled.
- The hold must identify the deactivated scope and affected Audit ID(s) in Manager 2.0 and, where operationally relevant, Auditor 2.0.
- Config_Scopes deactivation blocks use of the scope for new planning/cycles while inactive, but does not destructively erase historical scope/obligation/visit truth.
- Resolution must use explicitly governed scope/lifecycle actions and canonical validation; no hidden status rewrite and no pseudo-status solely for the hold.
- Scope deactivation and resolution require audit trail and targeted invalidation.


21.27 Availability ownership after planning
- A committed planned audit owns its occupied Availability intervals through Planning JSON projection. Those occupied intervals are read-only in My Availability and cannot be overwritten by a later personal Availability edit.
- Therefore an Auditor cannot create a contradiction by marking the already planned audit interval unavailable; changing the audit itself must use the governed planning/Re-adjust/Cancel flow.
- Planning 2.0 must preserve this protection and distinguish audit-owned hard occupancy from editable personal Availability.
- Availability UI rollback/read-only behavior must remain deterministic and must not mutate lifecycle status.


21.28 Company planning preferences remain advisory
- Less-suitable weekdays/hours and Preferred audit months are company planning preferences / soft blocks only. They never become hidden hard constraints.
- A later accepted company-data proposal that changes these preferences does not invalidate or place a hold on an already Approved/Accepted audit.
- Planning/Re-adjust surfaces show relevant preference mismatches as advisory context when a planning decision is being made, but committed lifecycle truth is not rewritten solely because preference metadata changed.


21.29 Company identity and retirement
- Company_UID is the stable canonical company identity used for joins between Companies, active audits, proposals, scope/cycle ownership and supporting read models. Company name is display data, not identity.
- Normal operations retire/deactivate a Company rather than physically deleting its canonical row. Historical audits, completed/rejected records and audit trail must remain resolvable to the original Company_UID.
- Duplicate-company merge is not treated as an ordinary edit. If introduced, it requires an explicit governed migration with referential-integrity checks across Model C, Audit planning, history, proposals, locations and notifications.
- Planning 2.0 must not introduce company-name fallback matching where Company_UID is available.


21.30 Scope Manager versus current Visit boundary
- Scope Manager owns Company Scope / obligation lifecycle. It must distinguish future-cycle maintenance from a mutation of scopes linked to the current open Visit.
- Future-only scope/certificate changes follow 21.12 and do not rewrite the current Visit.
- Adding, removing or materially changing a scope that is linked to the current planned Visit is a planning mutation and follows 21.6: the current committed plan is no longer silently treated as valid.
- Scope Manager must show the impact before commit when a change touches an open Visit, including affected Audit ID, required hours/window/dependency consequences and resulting lifecycle action.
- No scope edit may silently unlink historical Visit_Obligation relationships or erase certificate history.


21.31 Same-company concurrent audits
- Overlapping audits for the same Company, including the same execution location, are allowed when they are assigned to different canonically available/eligible Auditors and all auditor-specific hard validators pass.
- Same-company and especially same-location time overlap produces a clear planning warning so the planner can verify that concurrent auditing is operationally intended.
- This warning is advisory only and does not become a hard block by itself.
- Planning 2.0, Re-adjust and later batch/bulk planning use the same rule and warning semantics.


21.32 Auditor same-day capacity semantics
- The canonical Availability interval model permits more than one non-overlapping audit block for the same Auditor on one day; it is not a one-audit-per-day model.
- Overlap with another committed audit remains a hard block.
- Long working days / high same-day total planned hours remain a soft warning under Availability governance, not an automatic hard block solely because a nominal daily-hours threshold is exceeded.
- Travel feasibility between same-day visits is validated separately and may produce the applicable travel/conflict outcome; later trip/workweek planning reuses the same canonical inputs.


21.33 Travel feasibility and dual audit-duration semantics
- Travel infeasibility between two otherwise non-overlapping same-day audits is advisory, not a hard planning block. Planning may be committed with a prominent warning; the Manager remains responsible for practical feasibility.
- Preserve the established distinction between Formal hours and Planning duration. Config_Scopes is the structural owner for both concepts: Formal hours is the normative/audit-accounting duration; Scheduling_hours / Planning duration is the practical duration used to construct the agenda and assess day/travel feasibility.
- Company-specific Formal hours may override the Config_Scopes Formal-hours norm through Company Scope ownership. Planning duration remains per-scope in Config_Scopes; there is no Company Planning-duration override in the current model.
- Capacity, calendar blocks, same-day sequencing and travel feasibility use Planning duration / committed Planning JSON, not Formal hours as a proxy.
- Formal-hours reconciliation remains separately visible so a practically shorter/longer calendar construction cannot silently change the formal audit-hour obligation.


21.34 Multi-scope Planning duration aggregation
- For a Visit containing multiple scopes, practical Planning duration is the sum of the applicable Config_Scopes Scheduling_hours values for those scopes.
- No implicit bundling discount or overlap/compression rule is applied. Example: scope A Scheduling_hours 6 plus scope B Scheduling_hours 2 yields 8 practical planning hours.
- The summed Planning duration drives agenda capacity, calendar construction and travel/day-feasibility context; Formal hours remain the separate normative/accounting concept defined in 21.33.
- Any future exception to additive Scheduling_hours must be explicitly represented in canonical configuration/governance rather than inferred by UI or planner logic.


21.35 Planning duration tolerance
- Preserve the established Planning 1.0 tolerance when validating committed Planning JSON against calculated Planning duration.
- The normal target is exact equality: if calculated Planning duration is 8:00, the planner should plan 8:00.
- A maximum absolute deviation of 15 minutes is accepted for practical scheduling. This preserves the existing Planning 1.0 tolerance of ±0.25 h; Planning 2.0 must migrate that established rule rather than redefine it. A deviation greater than 15 minutes is a hard planning-validation failure and blocks commit.
- The tolerance applies to the total practical Planning duration for the Visit after additive multi-scope aggregation under 21.34; it does not alter Formal hours.
- Planning 2.0 must reuse this rule consistently for Manager planning, Auditor self-planning, Re-adjust and later batch/bulk planning.


21.36 Completion hours are actuals, not planning truth
- Hours dedicated entered at Completion are realized/actual audit effort and remain distinct from Planning duration and Formal hours.
- Completion does not require Hours dedicated to equal planned hours or Formal hours. The value must satisfy the canonical completion input rules (including quarter-hour granularity) and is archived as realized history.
- Planned-versus-dedicated variance is reporting/analysis input; it does not retroactively rewrite Planning JSON, Config_Scopes Planning duration or Company Scope Formal hours.
- Planning 2.0 reporting should preserve all three concepts explicitly: Formal hours, planned practical duration, and Hours dedicated.


21.37 Multi-scope planning-window intersection is mandatory
- For a combined Visit containing multiple scopes, the canonical planning window is the intersection of the applicable scope/obligation windows.
- If that intersection is empty, the combined Visit cannot be planned. The legacy UNION_FALLBACK behavior is not carried into Planning 2.0 as a valid commit path.
- Empty intersection is a hard planning-validity failure. The planner must first resolve the scope/cycle structure; in the normal case this may mean that the scopes require separate physical Visits/audits rather than one combined audit.
- The UI must show which scope windows conflict and make the reason for the block explicit. It must not silently widen the allowed period.
- Model C obligation/visit ownership determines whether scopes can be linked to one Visit; UI grouping cannot override incompatible canonical windows.


21.38 Empty-intersection resolution creates separate Visits, not widened truth
- When 21.37 blocks a combined Visit because scope windows do not intersect, the governed resolution is to review the underlying obligations and, where certification rules permit, split them into separate physical Visits/audits with their own Audit IDs and valid planning windows.
- Splitting must preserve Company Scope and Audit Obligation identity/history and create explicit Audit_Visit_Obligations links; it is not implemented by duplicating scope text or manually cloning an Audit planning row.
- Scope dependencies may prohibit a split. Parent/add-on, shared-expiry or must-audit-together rules take precedence; if such a dependency conflicts with the calculated windows, the underlying cycle/configuration requires correction rather than a planning override.
- Planning 2.0 should surface the likely split resolution to the Manager but must not automatically create extra Visits without an explicit governed action.


21.39 Dependent scopes cannot be split into separate Visits
- Scopes with a canonical must-audit-together/certification dependency, including MPS-GAP + GRASP where that dependency applies, cannot be resolved as separate physical Visits merely to bypass incompatible planning windows.
- If dependent scopes produce an empty planning-window intersection, planning remains hard blocked and the underlying cycle, expiry, dependency or window data must be corrected first.
- Administrative linkage between two separate Visits is not a substitute for a must-audit-together dependency.
- Dependency validation therefore runs before any split-Visit resolution offered under 21.38.


21.40 Reactivation does not automatically release operational holds
- Reactivating a Company, Auditor, Config_Scope or planned execution location does not automatically release an operational hold that was created because that entity became inactive.
- The hold remains until a Manager explicitly releases/resolves it after the canonical validators have been rerun successfully.
- Reactivation may remove the underlying invalid condition, but it is not itself an audit lifecycle/planning action and must not silently resume progression.
- Manager 2.0 must show that the original inactive condition has been resolved and provide the governed release action; release actor/timestamp and validation outcome are audit-trailed.
- No pseudo-status is introduced; the audit retains its lifecycle status while the operational hold remains.


21.41 Annual workload uses both Formal hours and Planning duration without conflation
- Annual workload/capacity surfaces preserve the established dual view: Formal hours, Planning duration, and audit count are separate planning dimensions.
- Formal hours represent normative/audit-accounting workload to be delivered; Planning duration represents practical calendar capacity consumed by the Visit.
- Auditor capacity, occupied time, remaining headroom, agenda construction and trip/day feasibility use Planning duration / committed Planning JSON.
- Formal-hours-to-plan and formal-hours reconciliation remain separately visible for contractual/certification workload control.
- Hours dedicated remains realized history after Completion and is used for variance/reporting, not prospective capacity.
- Bundled scopes must not be double-counted as multiple physical Visits: formal scope workload may aggregate while physical Visit count and practical Planning duration follow the canonical Visit structure and 21.34.


21.42 Pending-Planning preassignment transfer
- Preassignment is Manager-owned workload guidance while an audit remains Pending Planning; it is not a committed planning assignment and does not reserve Availability.
- The Manager may change preassignment directly from Auditor A to Auditor B while the audit is Pending Planning.
- After commit, Auditor A immediately loses self-planning access for that audit and Auditor B becomes the eligible self-planning owner, subject to canonical qualification/rotation and other validators.
- No confirmation, acceptance or handover action by Auditor A is required because no planning has yet been committed.
- The preassignment change is audit-trailed and must invalidate only the relevant Auditor/Manager workload projections.


21.43 Preassignment eligibility and rotation governance
- Preassignment is not a bypass around canonical Auditor eligibility. Candidate selection must expose Qualification and Rotation outcomes before the Manager commits the preassignment.
- Missing required Qualification is a hard block for preassignment because the auditor cannot become the self-planning owner for an audit they are not qualified to perform.
- Rotation follows 21.4 at preassignment time: within Config_Scopes maximum is allowed; maximum +1 requires the explicit warning/permission path; maximum +2 or beyond is blocked.
- Availability is not reserved by preassignment. Date-specific Availability is therefore revalidated at actual planning commit, while known workload/capacity context remains advisory during annual preassignment.
- Preassignment recommendations/ranking may use region, continuity and workload as advisory factors only; canonical validators remain authoritative.


21.44 Rotation consecutive-chain semantics are preserved
- Rotation is evaluated per Company + Scope against completed history in Log realized audits through the canonical Rotation service.
- Missing audit years do not break a consecutive chain.
- The chain resets only when another auditor performs the same Company + Scope audit.
- Planning/preassignment checks use the historical chain before the candidate audit and apply the 21.4 threshold policy to the resulting next assignment.
- Multi-scope Visits evaluate rotation independently per required scope; the strictest resulting verdict governs whether that auditor may be assigned to the Visit.
- Planning 2.0 must not replace this with calendar-year adjacency, company-only counts or visit-row counts.


21.45 Rotation maximum +1 requires recorded permission
- A candidate at Config_Scopes rotation maximum +1 is not a silent warning/ordinary override. Planning or preassignment may proceed only after the Manager explicitly confirms that the required permission has been obtained.
- The confirmation records the Manager actor, timestamp and a short reason/note in the audit trail, together with the relevant Company, Scope, auditor and rotation count/threshold context.
- This confirmation does not weaken the maximum +2 hard block; +2 or beyond remains impossible through ordinary Manager/Auditor UI.
- The permission record is tied to the specific assignment/planning decision and must not become a reusable blanket waiver for later audits.


21.46 Availability semantics preserved in Planning 2.0
- Auditor Availability remains the canonical capacity layer; Planning 2.0 must preserve the distinction between explicit hard unavailability and recurring/default soft unavailability.
- Explicit unavailable periods/dates are hard planning blocks. Existing committed audit intervals remain read-only audit-owned reservations and cannot be overwritten from My Availability.
- Recurring unavailable weekdays are soft unavailability: visible warning/advisory context that may be overridden through the governed planning path; they are not silently converted to hard blocks.
- Availability UI and planning validators must expose the same resolved semantics; no separate Manager interpretation may be introduced.
- Annual capacity reports hard unavailable hours, soft unavailable hours, occupied audit hours and overrideable soft hours separately.


21.47 Availability edits cannot overwrite committed audit occupancy
- My Availability may create explicit unavailable dates/ranges around existing work, but days/intervals already occupied by committed planned audits are skipped/protected rather than rewritten.
- An Auditor who becomes unavailable for an already planned audit must use the audit lifecycle/planning route (Cancel/Re-adjust or Manager intervention as applicable); changing personal Availability is not an indirect reschedule mechanism.
- Availability writes must therefore fail closed or skip protected audit-owned intervals deterministically and report what was not changed.
- This preserves Planning JSON as planning truth and prevents Availability from becoming a competing lifecycle owner.


21.48 Company update proposals require optimistic concurrency protection
- A Company_Update_Proposal is reviewed against the Company value that existed when the proposal was created (`Old_Value`).
- At apply time, the canonical Companies value must still equal that recorded Old_Value. If it differs, application is blocked as a stale/conflicting proposal; the proposed value must not overwrite the newer Company value.
- Manager 2.0 shows Old_Value, current canonical value and Proposed_Value together and requires a fresh review/decision against the current value.
- A stale proposal may be rejected/superseded and replaced by a new proposal/review decision; it is never silently rebased.
- This concurrency guard applies per affected field/location value so unrelated Company changes do not invalidate independent proposal fields.


21.49 Controlled administrative corrections after Completion
- Completed remains lifecycle-immutable: a completed audit is not reopened, moved back to an active status, replanned or reassigned through the correction path.
- Manager 2.0 provides a controlled correction action for realized administrative data in Log realized audits where correction is operationally necessary, including Hours dedicated.
- Every correction requires an explicit reason and records Manager actor, timestamp, Audit ID, field, previous value and corrected value in the audit trail.
- Corrections must pass field-specific validation (including the canonical Hours dedicated input/granularity rules) and use the canonical completed-audit writer/service; direct frontend/sheet mutation is not permitted.
- A correction changes realized/reporting truth only. It must not rewrite historical Planning JSON, Formal hours, Planning duration, completion provenance or lifecycle timestamps unless that specific field is itself governed as an administratively correctable field.
- Rotation/history cache invalidation remains targeted and deterministic where the corrected realized field can affect downstream projections.


21.50 Bulk planning supports explicit partial commit
- Bulk planning is not all-or-nothing. After commit-time canonical revalidation, valid items may commit while invalid items remain unchanged.
- Every item returns an explicit outcome such as committed, blocked, failed, already committed or skipped, with the governing reason where not committed.
- A hard validator failure for one audit must not prevent independent valid audits in the same batch from committing.
- No item may be silently omitted. The batch result must reconcile requested item count against every per-item outcome.
- Each committed audit still uses the canonical single-audit planning/write chain, including Planning JSON, Availability ownership, lifecycle action, audit trail and targeted cache invalidation; bulk orchestration must not become a second persistence owner.
- Batch/command idempotency is mandatory so timeout/retry cannot duplicate successful commits. Already committed items must be recognized deterministically on retry.


21.51 Bulk planning reuses per-audit notification semantics
- Bulk orchestration does not invent a second notification lifecycle. Each successfully committed audit emits the same canonical lifecycle event(s) that the equivalent single-audit action would emit through StatusNotificationBridge / Notification Queue.
- Blocked, failed or skipped bulk items emit no success lifecycle notification.
- Existing Notification Queue consolidation/digest rules may combine delivery where configured; bulk planning itself must not suppress, merge or directly send lifecycle mail.
- Notification idempotency remains payload/event based so batch retry does not create duplicate notifications for already committed items, while a legitimate later cancel/replan/accept cycle for the same Audit ID can still create new events.
- ECAS/external notifications remain tied to the canonical Accepted transition and existing external digest governance, irrespective of whether the underlying planning originated from single or bulk planning.


21.52 Multi-location Visits require explicit Planning-duration allocation per required location
- Where one audit/Visit requires multiple execution locations, the practical Planning duration is allocated explicitly across those required locations before planning can commit.
- The sum of the per-location Planning durations must equal the canonical total Visit Planning duration, subject to the existing ±15 minute total planning tolerance only where that tolerance is applicable to the committed blocks.
- Every required location must have its own positive configured/planned duration and at least one corresponding Planning JSON block carrying that execution location; a location cannot be satisfied by presence alone without its required time allocation.
- Planning JSON remains the committed time/location truth: block durations per `execLoc` must reconcile to the required per-location allocation.
- Location allocation is practical scheduling capacity and does not split or duplicate Formal hours. Formal hours remain governed separately under 21.41.
- Multi-day and non-consecutive planning may distribute a location's allocated duration across multiple blocks/days, provided the aggregate per location validates.
- Re-adjust of time/location must rerun both total-duration and per-location-duration validation before commit.


21.53 Multi-location duration allocation requires canonical configuration outside Planning JSON
- The required per-location Planning-duration allocation introduced in 21.52 is planning input/master data, not something inferred from or owned by the committed Planning JSON.
- Planning JSON stores the actual committed blocks and execution locations; it is validated against the canonical required allocation but does not define that requirement.
- Planning 2.0 therefore requires an explicit canonical data-model field/structure for required Visit locations and their Planning-duration allocations, keyed by stable Company_UID/location identity and the applicable audit/obligation context.
- Existing Companies.Locations_JSON remains the authoritative set of Company locations and their identity/contact/GPS metadata; duration allocation must reference those locations rather than duplicate location master data.
- The new allocation structure must support HQ plus secondary locations, total-duration reconciliation, history/audit trail and Model C projection without introducing positional S1/S2 assumptions as canonical identity.
- Until this structure exists and is migrated, 1.0 multi-location block data is compatibility input only and must not be mistaken for the new duration-allocation SSoT.


21.54 Active Company locations and required Visit locations are distinct concepts
- Companies.Locations_JSON remains the SSoT for the set of active/inactive Company locations. `Locations_to_plan` is a legacy/derived count of active locations and is not sufficient to define which locations a particular Visit must cover.
- Planning 2.0 must explicitly resolve the required execution-location set for each Visit/obligation context before applying the 21.52 duration allocation.
- Adding an active Company location does not by itself silently add that location to every existing/open Visit. Removing/deactivating a location follows the planned-location hold rule already defined for affected Visits.
- Required Visit-location membership and its duration allocation are versioned/audit-trailed planning requirements; Company location master-data edits remain separate.
- Legacy `Slot_Templates` and location-count behavior may be used for migration evidence but may not remain the canonical definition of required Visit locations in 2.0.


21.55 Required execution locations are configured per Company Scope
- Required execution-location membership is canonical Company Scope configuration, not a free per-cycle planning choice.
- For each active Company Scope, the Manager can define which active Companies.Locations_JSON locations are required for that scope and the corresponding practical Planning-duration allocation.
- Every new Audit Obligation/cycle for that Company Scope inherits the then-current required-location configuration as its planning requirement.
- An active Company location that is not selected for a Company Scope remains valid Company master data but is not required for audits of that scope.
- Changes to Company Scope required locations are lifecycle-governed like other scope configuration changes: future-only changes affect future obligations; a change intended to affect the current planned Visit follows the materiality/Re-adjust and hold rules already defined.
- For a combined multi-scope Visit, required locations are the union of the participating Company Scopes' required-location sets. Duration contributions remain traceable per contributing scope; where scopes share a location, those contributions aggregate at that one location rather than duplicating the location requirement. The resulting per-location totals must reconcile to the additive combined Planning duration under 21.56.


21.56 Per-location duration allocations must reconcile with additive multi-scope Planning duration
- The Company Scope location-duration model must preserve 21.35: combined-scope Visit Planning duration is the sum of the participating Config_Scopes Scheduling_hours unless an explicit future governance exception exists.
- Therefore the resolved per-location allocations for a combined Visit must sum to that same canonical combined Planning duration; location configuration may distribute the duration but may not implicitly discount or inflate it.
- If multiple participating scopes require the same location, the resolver must not blindly duplicate a location row. It produces one Visit-level requirement for that location while preserving traceability to every contributing Company Scope.
- A configuration that cannot reconcile its per-location allocations to the canonical total is a hard configuration/planning-validity error and cannot be committed.
- Scope Manager must validate this reconciliation when Company Scope location requirements are changed, before those requirements can govern a new Visit.


21.57 Company Map is a shared read model, not a planning owner
- Planning 2.0 preserves the existing Company Map as a shared visualization surface over Companies.Locations_JSON and audit workload; it must not create a parallel Company/location/planning dataset.
- Auditor workload overlay preserves separate visibility of own assigned/preassigned workload and other future active audits, using canonical Audit ID, Company_UID, status, auditor assignment and Planning JSON-derived schedule context.
- With 21.52-21.55, a multi-location Visit must project every committed execution location represented in Planning JSON to the corresponding Company location marker; the map may not collapse the Visit to the legacy single Audit planning Location field.
- Pending Planning preassignment may be visualized as prospective workload but remains distinct from committed planned occupancy.
- Company Map remains read-only/advisory. Planning, preassignment, lifecycle, Availability and Company mutations continue through their canonical owners.
- Map datasets must use bounded/cached/read-model access consistent with 3S and must not regress to per-marker or per-audit full-sheet scans.


21.58 Trip/workweek planning consumes committed location requirements without becoming a second planner
- Trip/workweek planning uses the Company Scope required-location model from 21.52-21.56 as input. It may sequence required execution locations across days but may not redefine which locations or durations are required.
- Travel is evaluated as a continuous itinerary between actual Visit blocks/locations, auditor base, hotel and transport nodes; no fictitious automatic return-to-base between audit days.
- Travel modes include car, train and flight where relevant. Comparison exposes door-to-door time, practical feasibility, schedule impact, reliable cost where available and sustainability burden.
- Flight carries an explicit environmental penalty/soft score but is not automatically hard-blocked. Travel infeasibility remains a prominent advisory warning under the existing Manager-responsibility rule rather than a lifecycle validator hard block.
- Hotel options/context are map/advisory inputs and may act as day start/end points; initial scope does not autonomously book hotels or transport.
- Trip concepts remain non-canonical until the underlying per-audit planning commits through the shared Planning 2.0 validators/writers. Partial bulk commit follows 21.50.


21.59 Company planning confirmation remains post-cutover roadmap scope
- Company proposal/confirmation is not a prerequisite for Planning 2.0 feature-parity cutover because no equivalent canonical Planning 1.0 workflow exists to migrate.
- It remains a later product capability after core Manager/Auditor parity, 3S acceptance and canonical planning migration are proven.
- Company feedback may confirm/decline/propose availability but never writes final Planning JSON, Availability occupancy or lifecycle status directly; feedback returns to Planning Workspace and all validators rerun before Manager/Auditor canonical commit.
- Notification Queue remains the delivery owner; email/portal response data is not a second planning truth.


21.60 Export parity is role-scoped and read-model based
- Auditor 2.0 preserves the proven multi-select audit export workflow: selected Audit IDs can be exported to Excel or PDF through a canonical successor of AuditorV5_ExportSelectedAudits.
- Export authorization remains role/data scoped; an Auditor export may contain only audits the authenticated Auditor is entitled to view. Client-supplied auditor identity is not sufficient authorization in the 2.0 security model.
- Manager reporting/export capability is delivered from the shared reporting read models in section 7 rather than by reusing Auditor-specific authorization or rebuilding calculations in the browser.
- Completed/history export consumes immutable realized/history read models, including controlled corrections under 21.49 as current realized truth while retaining correction provenance in audit trail.
- Export generation stays outside first-paint/hot paths and must not force portal-wide archive hydration.


21.61 Company update proposal queue prevents competing pending edits
- Planning 2.0 treats Company_Update_Proposals as a field-level review queue keyed by Company_UID + Section + Field_Key + Location_Code where applicable.
- There may not be multiple independently actionable Pending proposals for the same canonical field/location target. A new proposal for a target that already has a Pending proposal must surface the existing proposal and require resolution/supersession rather than silently adding a competing write.
- Multi-field submissions remain one user proposal context but each field retains its own review/concurrency outcome; one stale/conflicting field under 21.48 does not justify overwriting it or silently discarding independent valid fields.
- Manager review shows proposer, source Audit ID, old/current/proposed value and conflict state. Accept/reject/supersede outcomes are audit-trailed.


21.62 Handover information is layered and does not overload Company comments
- Existing Companies.Comments remains Company master-data commentary and continues to flow through the governed Company proposal/edit path; it is not silently redefined as the complete handover system.
- Future structured handover uses two explicit levels as already scoped in section 13.3: Company Handover for durable site/company instructions, and Audit/Visit Handover for cycle/visit-specific operational information.
- Planning JSON `slotComment` remains block-level planning context and is not a substitute for durable Company Handover or Visit Handover records.
- Handover data is advisory/operational context, permission-aware and audit-trailed where mutated; it does not own lifecycle, Availability, Company identity or planning requirements.
- Planning Workspace, Auditor Dashboard, Company Map/trip context and notifications may consume the same handover read model without copying the notes into separate truths.


21.63 Attention ageing uses canonical lifecycle timestamps
- Manager Cockpit ageing for Pending Approval, Approved/not Accepted and other active lifecycle states is derived from canonical lifecycle metadata, primarily `Status since`, not from UI load time, notification timestamps or inferred planned dates.
- Lifecycle transitions must write/update Status since through AuditLifecycleService/status ownership; missing Status since is data-integrity backlog to surface, not a reason to invent an age.
- Date - Approved / acceptance/decision timestamps remain event-specific provenance and may enrich drilldown, but do not replace the generic current-status age clock.
- Ageing thresholds are presentation/attention policy and must be configurable rather than encoded as lifecycle transitions or hard planning blocks.


21.64 Preferred audit months remain advisory in annual planning
- Preferred audit months are Company planning preferences, not certificate/planning-window truth and not hard eligibility constraints.
- Annual Planner and assignment advisory should use them to rank/highlight suitable months inside the canonical obligation planning window; planning outside a preferred month remains possible when all hard validators pass.
- A preferred month outside the canonical planning window never widens that window. The hard Model C window remains authoritative.
- Preference changes do not reset or hold existing Approved/Accepted audits and do not rewrite Planning JSON.
- Auditor-proposed changes to preferred months continue through Company_Update_Proposals rather than direct Company mutation.


21.65 Annual Planner supports non-committing month + auditor concept assignment
- A Pending Planning obligation/audit may carry both a concept planning month and a preassigned Auditor before any concrete audit date/time is committed.
- This is forecasting/annual-assignment metadata only: it does not create Planning JSON, reserve Availability, change lifecycle status or constitute an auditor assignment for an actual Visit.
- The concept month must remain compatible with the canonical Model C planning window; preferred audit months under 21.64 may guide selection but do not widen the hard window.
- Preassignment remains governed by qualification, rotation and preassignment rules, including 21.42-21.45. Changing the preassigned Auditor transfers self-planning visibility immediately as defined there.
- Annual workload views may allocate forecast workload to the concept month and preassigned Auditor, but must distinguish it visibly from committed planned capacity/occupancy.
- Concrete Manager planning or Auditor self-planning later revalidates all canonical constraints and writes the actual Planning JSON independently of the concept month.


21.66 Concept month participates in forecast capacity, not committed occupancy
- Annual Planner projects the concept month + preassigned Auditor from 21.65 against that Auditor's monthly derived capacity so the planner can see forecast overload before concrete scheduling.
- Forecast demand uses canonical practical Planning duration for capacity consumption; Formal hours remain a separate workload measure under 21.41.
- Concept allocation never writes Availability occupancy. Committed Planning JSON blocks remain the only audit occupancy source.
- Forecast overload is a planning warning/decision signal, not by itself a lifecycle hard block: exact dates, soft Availability and travel are unresolved until concrete planning.
- Hard facts already known at concept time, such as inactive Auditor, missing qualification or a concept month wholly outside the canonical planning window, cannot be presented as a valid concept assignment.


21.67 Annual concept assignment is bulk-capable by design
- The Annual Planner must support selecting multiple Pending Planning obligations/audits and assigning/changing concept month and/or preassigned Auditor as one planner operation; this is the precursor to later bulk concrete planning, not a separate truth model.
- Bulk concept assignment uses the same per-item qualification, rotation, planning-window and concurrency validation as single-item assignment. It follows the partial-success governance in 21.50: valid items apply, blocked items remain unchanged with explicit reasons.
- The preview summarizes resulting forecast workload/capacity by Auditor and month before commit, including Formal hours, Planning duration and audit/Visit counts without conflation.
- No selected item gains Planning JSON, Availability occupancy or lifecycle progression merely through bulk concept assignment.


21.68 Preassignment and self-planning permission remain separate controls
- A preassigned Auditor does not automatically gain permission to self-plan. Self-planning requires the canonical Allow self planning setting for that obligation/audit in addition to preassignment and current eligibility.
- When Allow self planning = YES, the preassigned Auditor may see the Pending Planning item in the self-planning work queue; when NO, the preassignment remains forecast/manager-planning metadata only.
- Changing Allow self planning does not itself create planning, reserve Availability or change lifecycle status.
- If self-planning permission is removed while the audit is still Pending Planning and uncommitted, self-planning access is withdrawn. Once a plan has been submitted and lifecycle has progressed, subsequent handling follows the canonical lifecycle/Re-adjust rules rather than silently deleting submitted planning.


21.69 Preassignment/self-planning policy belongs to the current obligation, not immutable Company identity
- Existing 1.0 storage projects Preassigned Auditor and Allow self planning onto the active Audit planning row and Scope Manager edits them together with the active audit context. Planning 2.0 must not promote either field to permanent Companies master data.
- In Model C they are current Audit Obligation / annual-assignment policy metadata (or a dedicated assignment-policy record keyed to the obligation/cycle), projected to legacy Audit planning only while compatibility is required.
- Successor obligations may copy the prior policy as an explicit lifecycle default for continuity, but each new obligation owns its resulting values and the Manager can change them without rewriting historical cycles.
- This keeps annual concept assignment, self-planning access and historical provenance cycle-specific while Company_UID remains stable identity only.


21.70 Successor-cycle assignment defaults preserve continuity but are revalidated
- Existing AnnualCycleEngineV5 already carries Preassigned Auditor into a recurring successor while clearing actual Assigned auditor/planning state. Planning 2.0 preserves that continuity principle at the Model C obligation layer rather than relying on copied legacy rows.
- Carried preassignment is a default, not proof of current eligibility. On successor creation/first use it must be revalidated against active Auditor, qualification and current rotation governance; an invalid carried value is surfaced for Manager resolution and cannot grant self-planning access.
- Allow self planning may likewise be carried as an explicit policy default only when represented canonically for the successor obligation; effective self-planning still requires a valid current preassignment under 21.68.
- Actual assignment, Planning JSON, Availability occupancy, lifecycle decisions and prior-cycle comments/decision metadata are never inherited as committed state into the new cycle.


21.71 Concept planning month requires canonical Model C storage
- Repository review found no existing canonical Audit planning field for a non-committed concept month. Planning 2.0 therefore must not overload Date - Planned, Planning window from/to, Preferred audit months or Planning JSON to store it.
- Add concept month as explicit annual-assignment metadata keyed to Audit Obligation/cycle (for example canonical YYYY-MM month key), with legacy projection only if a compatibility consumer demonstrably requires it.
- Clearing/changing concept month is a forecast mutation only and must be independently audit-trailed/concurrency-guarded without touching committed planning fields.
- Once a concrete plan is committed, actual Planning JSON/date governs operational calendar reporting; the concept month remains forecast provenance or is marked fulfilled/superseded rather than being mistaken for actual planning truth.


21.72 Weekend planning preserves existing soft-warning semantics
- Planning 2.0 preserves the proven Planning 1.0 `DEFAULT_WEEKEND` behavior: an Auditor normally unavailable on weekends produces a visible soft warning, not an automatic hard block.
- Explicit hard unavailability entered for the weekend date/interval remains a hard block under 21.46; committed audit occupancy remains protected under 21.47.
- Annual forecast capacity may treat default weekend time as soft/overrideable capacity, but must not present it as ordinary free capacity without distinction.
- Manager/Auditor concrete planning must show the weekend warning consistently through the shared Availability validator; no separate UI-only weekend rule.


21.73 Planning JSON block model is the multi-location Visit execution truth
- The existing canonical planning payload already supports block-level `execLoc` and `slotComment` in addition to date/start/end/hours. Planning 2.0 standardizes this block model rather than introducing a separate per-location schedule store.
- For a multi-location Visit, every committed block carries the actual execution location; blocks may occur on the same or different audit days subject to canonical validators and the Visit's total Planning-duration requirement.
- Required-location coverage from Company Scope configuration is validated against the set/duration of Planning JSON blocks before commit. A Visit cannot be committed while a required execution location is missing or under-allocated beyond the permitted duration tolerance.
- Legacy single Location remains compatibility/display projection only and cannot override block-level execution truth.
- Existing arbitrary `Max 5 planning days` validation is a Planning 1.0 implementation ceiling, not a future business-rule owner. Planning 2.0 must replace it with a configurable/derived limit sufficient for the required-location and segmented Visit model, while retaining bounded payload/performance safeguards.


21.74 Required-location duration validation is aggregate by location within the Visit
- A required Company Scope location may be represented by one or more Planning JSON blocks across one or more audit days. Validation aggregates block hours by canonical location code before comparing them with the resolved required-location allocation.
- Splitting one location's work across blocks/days therefore does not create duplicate location requirements and does not change the Visit's canonical total Planning duration.
- The Visit-level total still follows 21.35 ±15-minute tolerance. Per-location allocation is a coverage requirement: planners may segment the work operationally, but cannot use segmentation to omit a required location or move its allocated work invisibly to another location.
- Location codes in committed blocks must resolve to active Companies.Locations_JSON entries that are valid for the Visit; free-text location labels are display compatibility only.


21.75 Annual capacity must not equate the 08:00-18:00 Availability display window with productive audit hours
- Planning 1.0 uses 08:00-18:00 as the Availability calendar/default block envelope and treats a day with no Availability block as available. That ten-hour envelope is not by itself a ten-hour daily audit-capacity entitlement.
- Annual Planner capacity therefore derives from the governed Auditor work profile/standard working-day assumptions plus explicit hard/soft Availability and committed Planning duration; UI calendar rendering bounds are not capacity SSoT.
- Until richer Auditor profile hours are configured, capacity assumptions must be explicit/configurable and visible in the annual view rather than inferred silently from Availability row width.
- Long same-day planned workload remains governed by 21.32 as a soft warning, so forecast capacity and concrete feasibility remain distinct concepts.


21.76 Auditor Planning Profile is the owner for forecast-capacity assumptions
- Section 13.1 is promoted from a vague future profile to the canonical home for Auditor-specific planning assumptions that are not qualification truth: standard working-day capacity, blocked weekdays, planning base/location, region preferences and other planning constraints.
- Qualifications remain owned by the existing qualification/eligibility layer; Availability remains the date/interval exception and occupancy layer. The profile must not duplicate either.
- Annual capacity under 21.41/21.75 derives its gross baseline from this profile (with explicit system defaults only where a profile value is absent), then applies hard/soft Availability and committed occupancy.
- Profile changes affect future forecast/advisory calculations and trigger targeted read-model invalidation; they do not silently rewrite committed Planning JSON or lifecycle status.
