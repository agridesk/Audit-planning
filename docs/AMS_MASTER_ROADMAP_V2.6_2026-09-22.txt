21.4 Rotation — canonical threshold policy
Config_Scopes owns the applicable rotation maximum per scope.
- current count <= configured maximum: allowed;
- configured maximum + 1: warning/exception path; planning is only permitted with explicit permission context and must remain visible/auditable;
- configured maximum + 2 or more: HARD BLOCK; planning is not possible.
No UI may silently weaken this policy. Canonical rotation validation remains the owner.

21.5 Self-planning and acceptance
- Manager-planned audit: Pending Planning -> Plan -> Approved; Auditor Accept -> Accepted.
- Auditor self-planning: Pending Planning -> Plan -> Pending Approval; Manager Approve -> Accepted directly. The auditor does not perform a redundant second Accept after submitting the self-planning.
- For a manager-planned Approved audit, Manager may Accept on behalf of the assigned Auditor when the Auditor has confirmed outside the system.
- Every Accepted transition records the actual actor. Manager-on-behalf acceptance additionally records the auditor on whose behalf acceptance occurred, source and reason/context. Acceptance provenance is auditable.

21.6 Controlled Re-adjust — materiality rule
Re-adjust remains an action/mode through Workspace -> Preflight -> canonical writer.
- Change of audit day/date: material -> return to Pending Planning and restart normal planning flow.
- Change of scope(s) affecting the current planned visit/audit: material -> return to Pending Planning and restart normal planning flow.
- Scope/certificate lifecycle changes that affect only future certification cycles/obligations and do not change the current planned visit are not a reason to reset the current audit status.
- Time change within the same audit day (for example 08:00-16:00 to 09:00-17:00): preserves the current lifecycle status, including Accepted, provided canonical Availability/conflict/planning-window validation passes. No renewed auditor acceptance is required solely for this same-day time change.
- When an Accepted audit keeps its status after such a manager-made same-day time change, the Auditor Portal must show a small, non-blocking warning/tooltip on that audit indicating that the manager changed the audit time. The signal remains visible until the auditor has seen/acknowledged the change; it is informational and does not introduce a new lifecycle status or acceptance step.
- Other non-material changes may preserve status when they do not change the audit day or scope set and pass the relevant canonical validators.
- Change of execution location while audit day/date, assigned auditor and scope set remain unchanged may preserve Approved/Accepted status, provided canonical Availability, travel/conflict and planning-validity checks pass. Execution-location change is not by itself a lifecycle reset trigger.
- Change of assigned auditor while date/day, scopes and planned time structure remain unchanged preserves the planning itself. The new auditor must explicitly accept the assignment before the audit can be Accepted; an already Accepted audit therefore returns to Approved for re-acceptance by the new auditor. Before reassignment is committed, canonical qualification, rotation, Availability, same-day capacity/overlap, travel/conflict and planning-validity checks must rerun for the replacement auditor; hard failures block reassignment.

- If a company/scope formal-hours change makes an already Approved/Accepted Visit under-planned, preserve the current lifecycle status. Surface a hard planning-validity warning/block until planned hours are corrected; do not silently reset lifecycle status. The audit cannot progress through planning-dependent downstream completion while this hard inconsistency remains.
- Completed remains immutable for operational Re-adjust.
This rule supersedes older generic wording that every time/hours/block change automatically resets lifecycle status.

21.7 3S performance — all user-facing mutation paths
Speed is a release criterion for every migrated/new 2.0 capability, not a later polishing phase.
Required hot mutations include at minimum:
- add/change/deactivate company audit scope and resulting hours recalculation;
- lifecycle/status transition;
- planning Save / Modify / Re-adjust / Cancel;
- extension apply/undo and resulting effective expiry/planning-window projection;
- company/planning-profile updates that affect planner decisions.
Targets:
- local UI response immediate where no server decision is required;
- common cached/read-model interaction < 1 s target;
- major decision-ready load approx. <= 2 s p95 where technically realistic;
- no normal mutation may trigger repeated multi-second full-sheet scans or broad rebuilds.
Required strategy: targeted/indexed reads and writes, compact read models, deterministic targeted invalidation, optimistic UI only where canonical response can safely reconcile, and no synchronous non-critical work that unnecessarily blocks the user response. Correctness/transactional invariants remain mandatory.
Performance acceptance evidence is required per migrated capability; functional parity alone is not sufficient.

21.8 Extension interaction
Extension apply/undo is a Model C obligation/cycle mutation, not Visit lifecycle truth. It must update effective expiry/planning-window projections through the canonical owner, invalidate only affected read models/caches, and return a refreshed decision result without a broad full-grid rebuild. Extension interaction is explicitly a 3S hot path.

21.12 Scope/cycle mutation status isolation
- Current Visit lifecycle status changes only when the mutation materially changes that current planned Visit.
- Adding/removing/changing a scope linked to the current planned Visit is material and follows 21.6.
- Company Scope / certificate changes that only affect future certification cycles or future obligations do not reset the current Visit status.
- Extension apply/undo is obligation/cycle-specific and does not by itself reset a current Visit status unless it materially changes that Visit's canonical planning validity; any resulting invalidity is handled explicitly by canonical validation, never by an implicit blanket status reset.
- Historical scope/certificate truth is never destructively deleted.


21.13 Company data and preferred-period mutation isolation
- Companies remains canonical company truth; Locations_JSON remains the sole canonical location owner.
- Auditor-originated company-data/preferred-period changes remain proposals until manager review/acceptance; they do not directly mutate Companies.
- Preferred audit months/period are planning guidance for future planning and do not by themselves alter the lifecycle status or committed Planning JSON of an already planned Visit.
- General company/contact/comment/constraint updates do not reset an active Visit merely because company master data changed. If a changed canonical field materially affects the current Visit (for example its selected execution location or another planning validator input), the current Visit is explicitly revalidated under 21.6 rather than blanket-reset.
- Accepted proposal application must use targeted cache/read-model invalidation and audit trail; no duplicate company truth and no broad rebuild.

21.14 Re-adjust confirmation and notification semantics
- A lifecycle-preserving Re-adjust must still create an audit-trail event containing actor, timestamp, changed fields and before/after values or equivalent deterministic change metadata.
- Material changes that require renewed approval/acceptance use the canonical lifecycle notification for the resulting state; informational changes that preserve status must not manufacture a lifecycle transition.
- Manager-made same-day time changes on Accepted audits use the informational auditor signal defined in 21.6. Similar informational signals may be used for other lifecycle-preserving changes only where operationally useful; they remain separate from status.
- Notification delivery failure never rolls back an otherwise valid canonical mutation; Notification Queue remains the delivery SSoT.


21.15 Company master-data parity and ownership
- Manager 2.0 must retain the existing Companies operational surface: list/search, create company, edit company, status, country/time zone, contacts, communication language, region, comments, planning preferences and Locations_JSON-backed locations.
- Manager company creation/editing writes through the existing canonical Companies backend; 2.0 must not introduce a second company store or duplicate write path.
- Auditor company adjustments remain proposal-only. Company_Update_Proposals is the staging/review path; manager review accepts/rejects and accepted changes are applied to Companies with audit trail.
- Preferred audit months and less-suitable weekdays/hours remain planning preferences/soft constraints, not hard planning blocks. Changes do not rewrite existing Planning JSON or lifecycle status by themselves.
- New companies must become available to Scope Manager / Model C ownership without manual cache repair; targeted invalidation/read-model refresh is part of acceptance.

21.16 Hard planning validity versus manager discretion
- Canonical hard planning failures remain non-overridable by ordinary Manager/Auditor UI actions: double booking/overlap, auditor unavailable, outside canonical planning window, invalid qualification/dependency, and other validator-defined hard failures.
- Manager discretion applies only to explicitly classified soft warnings/preferences. A UI acknowledgement may record the decision but may not convert a hard failure into a valid canonical plan.
- Weekend handling, travel burden, sustainability preference, company less-suitable days/hours and rotation pressure remain governed by their explicit rule classifications; rotation specifically follows 21.4.
- Planning 2.0 must render hard versus soft outcomes distinctly and reuse one canonical validator owner for Manager, Auditor, Re-adjust and later batch/bulk planning.


21.17 Archive/history and operational export parity
- Rejected remains terminal lifecycle history. 2.0 does not introduce a normal restore/reopen transition.
- Completed remains immutable operational history in Log realized audits. Corrections, if ever required, are a separately governed administrative process and not Re-adjust.
- Manager 2.0 exposes completed and rejected history through bounded/paged reads rather than hydrating archives on first paint.
- Auditor 2.0 preserves the existing selected-audit export capability, including Excel and PDF, through the existing backend contract or a compatible canonical successor.
- Export generation is not a first-paint dependency and remains outside portal hot paths.


21.18 Completion parity and provenance
- Completion remains a canonical lifecycle action from Accepted to Completed and uses CompletionService / StatusMachine ownership, never a direct UI archive write.
- Auditor completion records the actual auditor actor. Manager completion on behalf of the auditor remains supported and must preserve truthful provenance, including manager actor and on-behalf mode/reason where required by the canonical completion contract.
- Completion must preserve transactional ordering across validation, realized-audit history, recurring-cycle handling, Availability release and active-row retirement; partial completion is not an acceptable success state.
- Completion UI and history/export surfaces in 2.0 must reuse this owner rather than rebuilding completion logic.


21.19 Company deactivation with open audits
- Changing a Company to Inactive while it still has open Approved/Accepted audits does not silently invalidate, complete, cancel or archive those audits.
- Those open audits enter a hard operational hold: they cannot progress until a Manager makes an explicit decision for each affected audit or governed group of audits.
- The hold must be visible in Manager 2.0 and, where relevant, Auditor 2.0, with the Company inactive condition and affected Audit ID(s) clearly identified.
- Company deactivation also blocks creation of new audits/cycles for that Company while Inactive.
- Resolution must use an existing canonical lifecycle/planning action where applicable; no hidden status rewrite and no new pseudo-status solely for this hold.
- Deactivation and resolution decisions require audit trail and targeted cache/read-model invalidation.


21.20 Auditor deactivation with assigned open audits
- Deactivating an Auditor does not automatically rewrite lifecycle status for already assigned Approved/Accepted audits.
- Every affected open audit enters a hard operational hold until a Manager explicitly reassigns it; while held it cannot progress operationally under the inactive auditor.
- Reassignment then follows 21.6: existing planning is preserved when date/day, scopes and planned time structure are unchanged; all canonical replacement-auditor validations must pass; the new auditor must explicitly Accept before the audit can be Accepted.
- For an audit that was Accepted before the reassignment, the reassignment itself returns it to Approved for the new auditor's acceptance. The deactivation event alone does not perform that transition.
- The hold and affected Audit IDs must be visible to the Manager; no pseudo-status is introduced solely for the hold.
- Auditor deactivation, hold creation and reassignment require truthful audit trail and targeted invalidation.


21.21 Loss of auditor qualification after planning
- If an assigned Auditor is no longer canonically qualified for any required scope of an Approved/Accepted audit before execution, the audit returns to Pending Planning.
- This is a hard planning-validity failure, not an operational hold and not a soft warning.
- Existing planning may remain available as historical/replanning context, but it is no longer a valid committed plan and cannot preserve Approved/Accepted lifecycle state.
- Replanning must rerun qualification, rotation, Availability, overlap/capacity, travel/conflict, planning-window and other canonical validators before the audit can progress again.
- The qualification-loss transition requires audit trail, appropriate lifecycle notification and targeted invalidation.


21.22 Extension action stage boundary
- Apply Extension and Undo Extension are available only while the audit is in Pending Planning / planning stage.
- Once an audit has progressed to Pending Approval, Approved or Accepted, Apply/Undo Extension is not an available operational action.
- Therefore extension apply/undo cannot create an Approved/Accepted audit outside a restored planning window; roadmap and acceptance tests must not model that impossible transition.
- Extension mutation remains a pre-commit planning/cycle action and must be validated before the audit leaves Pending Planning.


21.23 Pending Approval is a review boundary
- Pending Approval represents an Auditor-submitted plan awaiting Manager review; it is not an Extension editing stage.
- Manager approval of Auditor self-planning follows the self-planning lifecycle rule in 21.5. The implementation must be migrated from the older generic Pending Approval -> Approved contract to the canonical direct-accept outcome defined there.
- If the Manager does not accept the submitted planning, the audit returns to Pending Planning through the canonical return/cancel/deny successor action; planning corrections are made there rather than silently editing an Auditor submission while approval remains pending.
- Approval/rejection review must show the submitted planning context needed for an informed decision without rebuilding Planning JSON client-side.


21.24 Multi-location planning parity
- Multi-location companies/audits are first-class planning input. One audit may require HQ plus one or more active secondary sites/stops.
- Companies.Locations_JSON remains the only authoritative location set; legacy Location, GPS-data and Locations_to_plan remain derived mirrors and may not determine visit truth independently.
- Planning JSON must retain the actual location per planned block/segment where multiple locations are involved; travel/conflict validation must use those actual visit locations rather than assuming HQ.
- Planning 2.0 must support the existing multi-day/non-consecutive/segmented planning model together with multi-location selection without introducing a second visit model.
- Future trip/workweek routing consumes these committed visit locations; it does not rewrite them as routing truth.


21.25 Deactivation of a planned execution location
- If a location in Companies.Locations_JSON is deactivated while an Approved/Accepted audit is committed to that location, lifecycle status is not automatically rewritten.
- The affected audit enters a hard operational hold and cannot progress until a Manager selects a valid active execution location.
- Selecting the replacement location follows the execution-location rule in 21.6: lifecycle status may remain when canonical Availability, travel/conflict and planning-validity checks pass.
- The hold must be visible to Manager and relevant Auditor views; no pseudo-status is introduced.
- Location deactivation, hold and resolution require truthful audit trail and targeted invalidation.


21.26 System-wide scope deactivation with open audits
- Deactivating a scope in Config_Scopes does not automatically rewrite lifecycle status for existing Approved/Accepted audits that contain that scope.
- Every affected open audit enters a hard operational hold and cannot progress until a Manager explicitly decides how that audit is to be handled.
- The hold must identify the deactivated scope and affected Audit ID(s) in Manager 2.0 and, where operationally relevant, Auditor 2.0.
- Config_Scopes deactivation blocks use of the scope for new planning/cycles while inactive, but does not destructively erase historical scope/obligation/visit truth.
- Resolution must use explicitly governed scope/lifecycle actions and canonical validation; no hidden status rewrite and no pseudo-status solely for the hold.
- Scope deactivation and resolution require audit trail and targeted invalidation.


21.27 Availability ownership after planning
- A committed planned audit owns its occupied Availability intervals through Planning JSON projection. Those occupied intervals are read-only in My Availability and cannot be overwritten by a later personal Availability edit.
- Therefore an Auditor cannot create a contradiction by marking the already planned audit interval unavailable; changing the audit itself must use the governed planning/Re-adjust/Cancel flow.
- Planning 2.0 must preserve this protection and distinguish audit-owned hard occupancy from editable personal Availability.
- Availability UI rollback/read-only behavior must remain deterministic and must not mutate lifecycle status.


21.28 Company planning preferences remain advisory
- Less-suitable weekdays/hours and Preferred audit months are company planning preferences / soft blocks only. They never become hidden hard constraints.
- A later accepted company-data proposal that changes these preferences does not invalidate or place a hold on an already Approved/Accepted audit.
- Planning/Re-adjust surfaces show relevant preference mismatches as advisory context when a planning decision is being made, but committed lifecycle truth is not rewritten solely because preference metadata changed.


21.29 Company identity and retirement
- Company_UID is the stable canonical company identity used for joins between Companies, active audits, proposals, scope/cycle ownership and supporting read models. Company name is display data, not identity.
- Normal operations retire/deactivate a Company rather than physically deleting its canonical row. Historical audits, completed/rejected records and audit trail must remain resolvable to the original Company_UID.
- Duplicate-company merge is not treated as an ordinary edit. If introduced, it requires an explicit governed migration with referential-integrity checks across Model C, Audit planning, history, proposals, locations and notifications.
- Planning 2.0 must not introduce company-name fallback matching where Company_UID is available.


21.30 Scope Manager versus current Visit boundary
- Scope Manager owns Company Scope / obligation lifecycle. It must distinguish future-cycle maintenance from a mutation of scopes linked to the current open Visit.
- Future-only scope/certificate changes follow 21.12 and do not rewrite the current Visit.
- Adding, removing or materially changing a scope that is linked to the current planned Visit is a planning mutation and follows 21.6: the current committed plan is no longer silently treated as valid.
- Scope Manager must show the impact before commit when a change touches an open Visit, including affected Audit ID, required hours/window/dependency consequences and resulting lifecycle action.
- No scope edit may silently unlink historical Visit_Obligation relationships or erase certificate history.


21.31 Same-company concurrent audits
- Overlapping audits for the same Company, including the same execution location, are allowed when they are assigned to different canonically available/eligible Auditors and all auditor-specific hard validators pass.
- Same-company and especially same-location time overlap produces a clear planning warning so the planner can verify that concurrent auditing is operationally intended.
- This warning is advisory only and does not become a hard block by itself.
- Planning 2.0, Re-adjust and later batch/bulk planning use the same rule and warning semantics.


21.32 Auditor same-day capacity semantics
- The canonical Availability interval model permits more than one non-overlapping audit block for the same Auditor on one day; it is not a one-audit-per-day model.
- Overlap with another committed audit remains a hard block.
- Long working days / high same-day total planned hours remain a soft warning under Availability governance, not an automatic hard block solely because a nominal daily-hours threshold is exceeded.
- Travel feasibility between same-day visits is validated separately and may produce the applicable travel/conflict outcome; later trip/workweek planning reuses the same canonical inputs.


21.33 Travel feasibility and dual audit-duration semantics
- Travel infeasibility between two otherwise non-overlapping same-day audits is advisory, not a hard planning block. Planning may be committed with a prominent warning; the Manager remains responsible for practical feasibility.
- Preserve the established distinction between Formal hours and Planning duration. Config_Scopes is the structural owner for both concepts: Formal hours is the normative/audit-accounting duration; Scheduling_hours / Planning duration is the practical duration used to construct the agenda and assess day/travel feasibility.
- Company-specific Formal hours may override the Config_Scopes Formal-hours norm through Company Scope ownership. Planning duration remains per-scope in Config_Scopes; there is no Company Planning-duration override in the current model.
- Capacity, calendar blocks, same-day sequencing and travel feasibility use Planning duration / committed Planning JSON, not Formal hours as a proxy.
- Formal-hours reconciliation remains separately visible so a practically shorter/longer calendar construction cannot silently change the formal audit-hour obligation.


21.34 Multi-scope Planning duration aggregation
- For a Visit containing multiple scopes, practical Planning duration is the sum of the applicable Config_Scopes Scheduling_hours values for those scopes.
- No implicit bundling discount or overlap/compression rule is applied. Example: scope A Scheduling_hours 6 plus scope B Scheduling_hours 2 yields 8 practical planning hours.
- The summed Planning duration drives agenda capacity, calendar construction and travel/day-feasibility context; Formal hours remain the separate normative/accounting concept defined in 21.33.
- Any future exception to additive Scheduling_hours must be explicitly represented in canonical configuration/governance rather than inferred by UI or planner logic.


21.35 Planning duration tolerance
- Preserve the established Planning 1.0 tolerance when validating committed Planning JSON against calculated Planning duration.
- The normal target is exact equality: if calculated Planning duration is 8:00, the planner should plan 8:00.
- A maximum absolute deviation of 15 minutes is accepted for practical scheduling. This preserves the existing Planning 1.0 tolerance of ±0.25 h; Planning 2.0 must migrate that established rule rather than redefine it. A deviation greater than 15 minutes is a hard planning-validation failure and blocks commit.
- The tolerance applies to the total practical Planning duration for the Visit after additive multi-scope aggregation under 21.34; it does not alter Formal hours.
- Planning 2.0 must reuse this rule consistently for Manager planning, Auditor self-planning, Re-adjust and later batch/bulk planning.


21.36 Completion hours are actuals, not planning truth
- Hours dedicated entered at Completion are realized/actual audit effort and remain distinct from Planning duration and Formal hours.
- Completion does not require Hours dedicated to equal planned hours or Formal hours. The value must satisfy the canonical completion input rules (including quarter-hour granularity) and is archived as realized history.
- Planned-versus-dedicated variance is reporting/analysis input; it does not retroactively rewrite Planning JSON, Config_Scopes Planning duration or Company Scope Formal hours.
- Planning 2.0 reporting should preserve all three concepts explicitly: Formal hours, planned practical duration, and Hours dedicated.


21.37 Multi-scope planning-window intersection is mandatory
- For a combined Visit containing multiple scopes, the canonical planning window is the intersection of the applicable scope/obligation windows.
- If that intersection is empty, the combined Visit cannot be planned. The legacy UNION_FALLBACK behavior is not carried into Planning 2.0 as a valid commit path.
- Empty intersection is a hard planning-validity failure. The planner must first resolve the scope/cycle structure; in the normal case this may mean that the scopes require separate physical Visits/audits rather than one combined audit.
- The UI must show which scope windows conflict and make the reason for the block explicit. It must not silently widen the allowed period.
- Model C obligation/visit ownership determines whether scopes can be linked to one Visit; UI grouping cannot override incompatible canonical windows.


21.38 Empty-intersection resolution creates separate Visits, not widened truth
- When 21.37 blocks a combined Visit because scope windows do not intersect, the governed resolution is to review the underlying obligations and, where certification rules permit, split them into separate physical Visits/audits with their own Audit IDs and valid planning windows.
- Splitting must preserve Company Scope and Audit Obligation identity/history and create explicit Audit_Visit_Obligations links; it is not implemented by duplicating scope text or manually cloning an Audit planning row.
- Scope dependencies may prohibit a split. Parent/add-on, shared-expiry or must-audit-together rules take precedence; if such a dependency conflicts with the calculated windows, the underlying cycle/configuration requires correction rather than a planning override.
- Planning 2.0 should surface the likely split resolution to the Manager but must not automatically create extra Visits without an explicit governed action.


21.39 Dependent scopes cannot be split into separate Visits
- Scopes with a canonical must-audit-together/certification dependency, including MPS-GAP + GRASP where that dependency applies, cannot be resolved as separate physical Visits merely to bypass incompatible planning windows.
- If dependent scopes produce an empty planning-window intersection, planning remains hard blocked and the underlying cycle, expiry, dependency or window data must be corrected first.
- Administrative linkage between two separate Visits is not a substitute for a must-audit-together dependency.
- Dependency validation therefore runs before any split-Visit resolution offered under 21.38.


21.40 Reactivation does not automatically release operational holds
- Reactivating a Company, Auditor, Config_Scope or planned execution location does not automatically release an operational hold that was created because that entity became inactive.
- The hold remains until a Manager explicitly releases/resolves it after the canonical validators have been rerun successfully.
- Reactivation may remove the underlying invalid condition, but it is not itself an audit lifecycle/planning action and must not silently resume progression.
- Manager 2.0 must show that the original inactive condition has been resolved and provide the governed release action; release actor/timestamp and validation outcome are audit-trailed.
- No pseudo-status is introduced; the audit retains its lifecycle status while the operational hold remains.
