3. 3S — HARD RELEASE CRITERION

3.1 Speed
- local UI response immediate where no server decision is required;
- common cached/read-model interactions target < 1 s;
- major decision-ready loads target approx. <= 2 s p95 where technically realistic;
- browser wall time matters, not only serverMs;
- normal actions may not repeatedly rebuild broad Sheet context.

3.2 Scalability
- bounded/windowed reads;
- no N+1 per audit/day/auditor/marker;
- shared read models;
- dynamic scope handling up to initial supported boundary of 20 active scopes;
- batch orchestration reuses per-item canonical chain;
- no fixed 8-scope assumptions in new 2.0 surfaces.

3.3 Stability
- deterministic targeted invalidation;
- hard validators fail closed;
- optimistic concurrency/revision protection;
- idempotency where retry can occur;
- truthful audit trail;
- canonical writers only;
- DEV/PROD discipline;
- rollback/recovery for multi-step writes.

3.4 GAS/RPC performance lessons that remain binding
- visible work always outranks speculative prefetch;
- speculative prefetch budget is zero while visible Save/Validate/Commit is pending;
- prefer coarse-grained/range payloads over multiple adjacent-month RPCs;
- one command context should be reused through equivalent validation phases;
- do not repeatedly reload audit/company/scope context inside one command;
- notification rendering/enrichment must not unnecessarily extend commit critical path;
- measure cold/warm wall time, queueing and transport contention.

4. PLANNING 2.0 PRODUCT BOUNDARY

Planning 2.0 replaces the slow Planning 1.0 interaction model. It is not a second planning engine.
Manager and Auditor converge on the same read models, validators, Concept model, Workspace, Preflight and canonical writers. Only permissions/actions/presentation differ.

The legacy Planning Toolkit is a migration surface, not an end-state product and not a separate optimization programme. Do not build a Toolkit 1.5.

Legacy surfaces remain only until equivalent 2.0 capability is functionally and 3S accepted.

5. CANONICAL LIFECYCLE

Canonical statuses:
Pending Planning -> Pending Approval -> Approved -> Accepted -> Completed
Rejected is terminal.

Manager-planned:
Pending Planning -> Plan by Manager -> Approved -> Auditor Accept -> Accepted.

Auditor self-planned:
Pending Planning -> Plan by Auditor -> Pending Approval -> Manager Approve -> Accepted.
No redundant second Auditor Accept after Manager approval of the Auditor's own submission.

Cancel/return:
Pending Approval / Approved / Accepted -> Pending Planning through canonical reopen/cancel handling.

Reject:
active -> Rejected terminal history.

Manager UX:
- user-facing CANCEL fuses legacy Cancel/Deny where the backend allows the corresponding return action;
- REJECT remains separate terminal action;
- APPROVE remains separate;
- PLAN belongs to Planning Workspace, not generic grid-action logic.

Manager Accept on behalf:
A Manager may Accept a manager-planned Approved audit for the assigned Auditor only when confirmation occurred outside the system. Record actual Manager actor, represented Auditor, source/channel, reason/context and timestamp. Never falsely log the action as performed by the Auditor.

6. CONTROLLED RE-ADJUST / MATERIALITY

No unrestricted generic Edit.
Re-adjust remains Workspace -> Preflight -> canonical writer.

Material:
- audit day/date change -> Pending Planning;
- scope change affecting current Visit -> Pending Planning.

Lifecycle-preserving when validators pass:
- same-day time/block change;
- execution-location-only change with same day/auditor/scope set.

Accepted audit + same-day Manager time change:
- remains Accepted;
- no renewed acceptance solely for the time change;
- Auditor receives a small non-blocking informational seen/acknowledged signal.

Auditor reassignment:
- planning may remain when day/scopes/time structure remain unchanged;
- qualification, rotation, Availability, overlap/capacity, travel/conflict and planning validity rerun;
- already Accepted -> Approved for new Auditor acceptance.

Formal-hours mutation causing under-planning:
- preserve current lifecycle status;
- surface hard planning-validity block until planning is corrected;
- do not silently reset lifecycle.

Completed:
- lifecycle-immutable;
- never reopened through Re-adjust.

Every lifecycle-preserving Re-adjust is audit-trailed with actor/timestamp/changed fields/before-after metadata.
Notification failure never rolls back an otherwise valid canonical mutation.

7. COMPLETION / REALIZED CORRECTIONS

Completion is canonical Accepted -> Completed and uses CompletionService / StatusMachine ownership.
Completion preserves truthful actor/on-behalf provenance and transactional ordering across validation, realized history, recurring-cycle handling, Availability release and active-row retirement.

Hours dedicated:
- realized actual effort;
- quarter-hour granularity under canonical completion rules;
- distinct from Formal hours and Planning duration;
- variance is reporting input only.

Post-completion correction:
- lifecycle remains Completed;
- Manager may make controlled administrative correction of governed realized fields, including Hours dedicated;
- reason mandatory;
- audit trail includes Manager actor, timestamp, Audit ID, field, old value, new value;
- no rewrite of historical Planning JSON, planning lifecycle or unrelated provenance.

8. SCOPE / CERTIFICATE / EXTENSION GOVERNANCE

Recurring=YES:
- certificate lifecycle/expiry applies;
- successor obligation follows lifecycle rules.

Recurring=NO:
- no invented certificate birthday/expiry;
- Cycle_Key may define annual/explicit obligation;
- no automatic certificate-style successor;
- blank explicit window with valid four-digit Cycle_Key may resolve operationally to that full calendar year where the accepted Model C rule applies;
- partial explicit window is invalid.

Scope Manager:
- owns Company Scope / obligation lifecycle mutation through Model C;
- distinguishes future-cycle maintenance from current-Visit mutation;
- never destructively deletes history;
- must show current-Visit impact before a material change.

Extension:
- Apply/Undo only while Pending Planning/planning stage;
- unavailable once Pending Approval, Approved or Accepted;
- obligation/cycle mutation, not lifecycle truth;
- updates effective expiry/window projection and targeted caches only.

Dynamic scopes:
- Config_Scopes-driven;
- initial design boundary 20 active scopes;
- adding/activating a supported configured scope must not require scope-specific code changes.

9. PLANNING WINDOW / DEPENDENCY RULES

Every obligation owns its canonical planning window.
Combined Visit window = intersection of participating obligation windows.
Empty intersection = HARD BLOCK.
No silent widening or UNION_FALLBACK.

Where certification rules permit, incompatible independent obligations may be resolved into separate Visits/Audit IDs with preserved obligation identity/linkage.
Must-audit-together/dependent scopes cannot be split merely to bypass incompatible windows. If their intersection is impossible, underlying cycle/expiry/dependency/window data must be corrected.

10. HOURS MODEL

Three distinct concepts are mandatory:
1. Formal hours — normative/audit-accounting workload; Config_Scopes default with Company Scope override where applicable.
2. Planning duration — practical agenda/capacity duration; Config_Scopes Scheduling_hours; no Company override in current model.
3. Hours dedicated — realized effort captured at Completion.

Multi-scope Visit Planning duration:
- sum Scheduling_hours of participating scopes;
- no implicit bundling discount/compression.

Committed Planning JSON duration:
- target exact canonical Planning duration;
- maximum absolute deviation ±15 minutes accepted;
- >15 minutes = hard planning-validation failure.

Annual planning must show Formal hours, Planning duration and audit/Visit counts separately and avoid double-counting bundled scopes.

11. AVAILABILITY / DAILY CAPACITY

Auditor Availability is the canonical capacity/exception layer.

Hard:
- explicit hard-unavailable interval/date;
- overlap with committed audit occupancy.

Soft/advisory:
- recurring/default blocked weekday;
- DEFAULT_WEEKEND behavior;
- high total same-day hours/long working day.

Committed audit occupancy:
- audit-owned/read-only in My Availability;
- personal Availability edit cannot overwrite it;
- Auditor unable for an already planned audit must use planning/lifecycle route.

Resolved priority semantics:
- committed occupancy and explicit hard unavailable take precedence over soft/default metadata;
- Calendar, Preflight, Annual Capacity and My Availability consume the same resolver semantics.

Same Auditor/day:
- multiple non-overlapping audits allowed;
- overlap hard-blocked;
- no automatic one-audit-per-day rule;
- no hard 17:00 boundary;
- no generic hard 9-hour audit+travel ceiling.

Same Company:
- overlapping audits allowed with different eligible/available Auditors;
- same Company and especially same location overlap gives a clear advisory warning, not a hard block by itself.

12. ROTATION

Config_Scopes owns maximum per scope.
- count <= maximum: allowed;
- maximum +1: only with explicit Manager confirmation that required permission was obtained;
- maximum +2 or beyond: HARD BLOCK.

+1 audit trail includes Manager actor, timestamp, reason/note, Company, Scope, Auditor and count/threshold context. Permission is assignment-specific, never blanket.

Consecutive chain:
- evaluated per Company + Scope against completed history;
- missing audit year does not break chain;
- another Auditor performing same Company + Scope resets chain;
- multi-scope Visit evaluates each scope and strictest verdict governs.

Rotation applies already at preassignment time.

13. PREASSIGNMENT / SELF-PLANNING POLICY

Preassignment while Pending Planning:
- Manager-owned forecast/workload guidance;
- does not reserve Availability;
- does not change lifecycle status;
- Auditor A -> B transfers directly; A confirmation not required;
- qualification hard-validates;
- rotation hard/exception policy applies;
- date-specific Availability revalidates at concrete commit.

Preassignment and Allow self planning are separate controls.
A preassigned Auditor gets self-planning access only when Allow self planning = YES and current eligibility passes.

Ownership:
- current Audit Obligation/cycle metadata, not immutable Company identity.

Successor cycle:
- preassignment / self-planning policy may carry as continuity defaults only;
- revalidate active Auditor, qualification and rotation;
- actual assignment, Planning JSON, Availability occupancy and lifecycle decisions never carry as committed state.

14. ANNUAL PLANNER / CONCEPT ASSIGNMENT

A Pending Planning obligation/audit may carry:
- concept planning month;
- preassigned Auditor;
without a concrete date/time.

Concept assignment:
- no Planning JSON;
- no Availability occupancy;
- no lifecycle change;
- concept month must fit canonical planning window;
- Preferred audit months are advisory only;
- hard known invalidity (inactive Auditor, qualification failure, concept month wholly outside window) cannot be presented as valid.

Canonical storage:
- concept month is explicit Model C annual-assignment metadata keyed to Audit Obligation/cycle;
- never overload Date-Planned, Planning JSON, planning-window fields or Preferred months.

Forecast:
- concept month + Auditor contributes to forecast capacity;
- Planning duration consumes forecast capacity;
- Formal hours remain separate workload measure;
- overload = planning warning, not lifecycle block by itself.

Bulk annual assignment:
- assign/change concept month and/or preassigned Auditor for multiple Pending Planning items;
- same per-item qualification/rotation/window/concurrency validation;
- explicit partial success;
- no Planning JSON/Availability/status mutation.

Concept month does not roll forward numerically to successor cycle. Successor derives candidate timing from its own planning window/current preferences and receives a newly assigned/confirmed concept month.

15. AUDITOR PLANNING PROFILE / CAPACITY

08:00–18:00 Availability display envelope is not automatically ten productive audit hours.

Auditor Planning Profile owns forecast assumptions not already owned elsewhere:

16. COMPANY MASTER DATA / PROPOSALS

Company_UID is stable identity. Company name is display data.
Normal retirement = deactivate, not physical delete.
Duplicate merge, if introduced, is a governed referential migration.

Companies remains master-data truth including Locations_JSON.
Manager 2.0 must retain create/edit/list/search/status/country/timezone/contact/language/region/comments/planning preferences/locations functionality through the canonical Companies backend.

Auditor-originated company changes remain proposal-only through Company_Update_Proposals.
Accepted proposal apply is targeted/audit-trailed and may not create a second Companies truth.

Optimistic concurrency:
- proposal stores Old_Value;
- apply requires current canonical value still equals Old_Value;
- otherwise stale/conflict block;
- Manager sees old/current/proposed;
- never silently rebase.

Proposal queue uniqueness:
- at most one independently actionable Pending proposal per Company_UID + Section + Field_Key + Location_Code target;
- multi-field submission preserves per-field outcomes.

Preferred audit months / less-suitable weekdays/hours:
- soft planning preferences;
- never widen hard planning window;
- do not reset/hold Approved/Accepted audits;
- Auditor changes remain proposal-based.

17. OPERATIONAL HOLDS / DEACTIVATION

Company inactive with open Approved/Accepted audits:
- no automatic status rewrite;
- hard operational hold;
- no new audits/cycles while inactive;
- Manager explicitly resolves.

Auditor inactive with assigned open audits:
- no automatic status rewrite;
- hard hold until Manager reassigns;
- reassignment follows canonical replacement-Auditor validation and acceptance rules.

Planned execution location inactive:
- no automatic status rewrite;
- hard hold until Manager selects valid active location.

System-wide Config_Scope inactive:
- no automatic rewrite of existing open Visit;
- hard hold;
- no new planning/cycles for inactive scope;
- history preserved.

Loss of required Auditor qualification after planning:
- direct hard planning-validity failure;
- Approved/Accepted -> Pending Planning;
- this is not merely a hold.

Reactivation:
- never auto-releases a prior hold;
- Manager explicitly releases/resolves only after canonical validators pass;
- actor/timestamp/validation outcome audited;
- no pseudo-status required.

18. MULTI-LOCATION PLANNING

Companies.Locations_JSON remains location master-data SSoT.
Active Company location != automatically required audit location.

Required locations:
- configured per Company Scope;
- each required location has canonical practical Planning-duration allocation;
- new obligations inherit then-current Company Scope requirement;
- combined multi-scope Visit resolves union of required locations;
- shared location contributions aggregate without duplicate location requirement;
- resolved per-location durations must reconcile to additive total Visit Planning duration.

Planning JSON:
- committed block-level execution truth;
- each block carries canonical execution location via execLoc;
- block durations aggregate per location;
- every required location must be covered with required time;
- multi-day/non-consecutive segmentation supported;
- legacy single Location is compatibility/display only;
- free-text label does not replace stable location identity.

Existing arbitrary max-five-planning-days ceiling is a 1.0 implementation ceiling, not future business policy. Replace with bounded/configurable/derived limits compatible with the segmented multi-location model.

19. COMPANY MAP / TRIP / WORKWEEK

Company Map:
- shared read-only visualization over Companies.Locations_JSON, audit workload and committed Planning JSON locations;
- no separate planning/location data store;
- pending preassignment may be shown as prospective workload distinct from committed occupancy;
- multi-location Visit must show all actual committed execution locations;
- bounded/cached, no per-marker/full-sheet N+1.

Trip/workweek:
- decision-support layer feeding Concept Planning/Workspace;
- never second planner or writer;
- uses required/committed Visit location requirements;
- continuous itinerary; no fictitious daily return to base;
- car/train/flight where relevant;
- compare door-to-door time, feasibility, schedule impact, reliable cost where available, sustainability burden;
- flight has explicit environmental penalty/soft score, never automatic hard block;
- travel infeasibility is prominent advisory warning, not lifecycle hard block;
- Manager retains practical responsibility;
- hotel context/options visible and may form day start/end points;
- no autonomous booking initially.

20. BATCH / BULK

Bulk concrete planning supports explicit partial commit.
After commit-time revalidation:
- valid items may commit independently;
- invalid items remain unchanged;
- every requested item has explicit outcome: committed / blocked / failed / already committed / skipped;
- no silent omission;
- hard failure on one item does not block unrelated valid items;
- each commit delegates to canonical single-audit writer;
- batch orchestration never becomes persistence owner;
- idempotency mandatory.

Notifications:
- each successful audit emits the same canonical lifecycle event as equivalent single action;
- blocked/failed/skipped items do not emit success lifecycle notifications;
- Queue/digest may consolidate delivery;
- bulk layer never directly sends lifecycle mail.

Later bulk Re-adjust / move-trip / controlled Auditor replacement must retain per-audit canonical validation.

28. DEFINITION OF DONE / CUTOVER GATE

A migrated capability is not DONE because a UI exists.
DONE requires:
- canonical owner identified and reused;
- functional parity or explicitly accepted replacement;
- accepted business rules from this roadmap enforced;
- no second truth/writer;
- role/authorization correct;
- status/Availability/notification/audit-trail effects defined;
- concurrency/idempotency where relevant;
- 3S evidence on realistic DEV data;
- regression tests;
- rollback/recovery for writes;
- legacy path retired only after replacement is proven.

Planning 2.0 cutover requires demonstrable Manager and Auditor operational parity for all currently used 1.0 functions that are not explicitly classified post-cutover.
