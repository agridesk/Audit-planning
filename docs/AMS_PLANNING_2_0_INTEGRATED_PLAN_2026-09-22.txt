AUDIT MANAGEMENT SYSTEM — PLANNING 2.0 INTEGRATED PLAN
Date: 2026-09-22
Status: PROPOSED CANONICAL INTEGRATED PLAN
Scope: Manager + Auditor planning, Availability, Concept Planning, Batch Planning, Re-adjust, Annual Workload/Capacity, Rotation, Trips
Operating principle: 3S + Value — Speed, Scalability, Stability + operational value

1. WHY PLANNING 2.0

Planning 1.0 is structurally too slow across the full planning chain. This is not a single Toolkit problem and should no longer be handled as a sequence of isolated performance patches.

Affected surfaces include:
- Manager Portal
- Auditor Portal
- Planning Toolkit
- Availability Calendar
- calendar first load
- month switching
- audit selection
- eligibility / qualification checks
- rotation checks
- Availability checks
- Save
- Modify / Re-adjust
- refreshes and overview reads
- annual planning overview

Planning 2.0 therefore becomes the umbrella programme for replacing the slow Planning 1.0 interaction model while preserving the proven canonical business logic and Model C ownership.

2. NON-NEGOTIABLE ARCHITECTURE

Canonical chain:
Company -> Company Scope -> Audit Obligation -> Audit Visit <-> Availability

Ownership:
- Model C owns scope lifecycle, obligations, cycles, expiry and visit-obligation linkage.
- Audit planning remains operational/compatibility projection and is not dismantled.
- Auditor Availability remains the operational Availability/capacity source.
- PlanningCanonicalModifyService remains the writer for controlled Modify/Re-adjust where applicable.
- Existing qualification, rotation, planning-window and Availability validators remain canonical.
- Notification Queue remains the delivery path.
- Git repository remains code SSoT.
- DEV GAS remains canonical development runtime.

Hard rules:
- no second planning engine;
- no second Availability model;
- no duplicate validator policy;
- no separate capacity truth;
- no silent dual truth;
- no direct bulk sheet edits;
- no UI-specific business rules that bypass canonical services.

3. TARGET PLANNING 2.0 FLOW

Planning Demand

This flow is shared by Manager and Auditor. Their permissions and available actions differ, but they do not use different planning engines.

4. CORE PRODUCT MODEL

4.1 Concept Planning
A Concept is a non-final planning proposal.

It may contain:
- Audit ID / obligation group
- auditor
- date
- time / blocks
- location
- scopes
- planning window
- qualification result
- rotation result
- Availability result
- warnings / waivers
- trip/workweek grouping
- revision/version

Concept Planning must support:
- individual planning;
- drag/drop or equivalent fast interaction;
- multiple audits before commit;
- safe recalculation;
- explicit hard blocks and soft warnings;
- no canonical write until Apply/Commit.

4.2 Planning Workspace
The Workspace is the operational decision surface.

Manager and Auditor use the same underlying read models and validators.

The Workspace must eventually replace the slow interaction pattern of Planning 1.0 for:
- choosing audits;
- choosing auditors;
- calendar interaction;
- editing concepts;
- validation;
- re-adjust;
- batch planning;
- trip/workweek planning.

4.3 Canonical Preflight
Every proposed planning action is revalidated immediately before write.

Preflight includes:
- qualification;
- planning window;
- Availability;
- rotation;
- status/lifecycle;
- Model C obligation linkage;
- concurrency/revision;
- required company/location constraints.

4.4 Canonical Commit
Only canonical services write operational planning.

Commit must be:
- transactional where required;
- idempotent where appropriate;
- guarded against stale revisions;
- traceable;
- notification-aware;
- rollback/recovery aware.

5. P0 — PERFORMANCE FOUNDATION

Planning 2.0 starts with system-wide performance, not UI cosmetics.

5.1 Availability Calendar Performance
Explicit P0/P1 workstream.

Measure and optimize:
- first load cold/warm;
- month switch cold/warm;
- auditor switch;
- refresh after save;
- refresh after modify/re-adjust.

Rules:
- month-bounded reads;
- no full-sheet scan on normal UI path;
- no N+1 per day;
- no N+1 per auditor;
- reusable indexed/read-model paths;
- cache-hit fast path;
- deterministic invalidation;
- correctness verification after cache use.

5.2 Planning Toolkit Performance — Manager + Auditor
Both current Toolkits are part of Planning 2.0 migration.

Measure:
- Toolkit open;
- audit select;
- auditor select;
- calendar decision-ready;
- month switch;
- validator refresh;
- Save;
- Modify/Re-adjust;
- post-save close/refresh.

The objective is not to keep adding patches to the old Toolkit indefinitely. Proven functionality is migrated into the Planning 2.0 Workspace.

5.3 Portal Performance
Manager and Auditor portals must use compact read models rather than repeatedly rebuilding operational truth from broad sheet reads.

6. P0 — OPERATIONAL UX HARDENING

6.1 Save & Close
Successful Save:
- exactly one commit;
- deterministic close where launch context permits;
- one safe fallback where browser close is technically impossible;
- no stale planning grid;
- no duplicate save.

6.2 Stable Workspace Interaction
- scroll stability;
- drag/drop stability;
- modal lifecycle stability;
- preserved context after non-destructive actions;
- predictable refresh after Save / Modify / Cancel.

6.3 Login / Entry
Direct entry into the correct Manager/Auditor surface after authorization where possible.

7. P0/P1 — CONTROLLED RE-ADJUST

Do not expose unrestricted generic “edit audit”.

Supported initial changes:
- date;
- time;
- block distribution.

Lifecycle:
- Pending Approval -> status preserved;
- Approved -> status preserved;
- Accepted -> Approved + renewed auditor acceptance;
- Completed -> blocked;
- unsupported states -> blocked.

Initial governance:
- same auditor only;
- auditor replacement is a separate high-impact action;
- Model C planning-window intersection is authoritative;
- old Availability released only within canonical modify transaction;
- new Availability reserved only after validation;
- notifications and audit trail follow canonical services.

Scope-aware Re-adjust:
- reads linked Audit_Obligations;
- respects dependencies;
- preserves historical obligations;
- never mutates an old annual obligation into a new cycle.

8. P1 — ANNUAL WORKLOAD + CAPACITY

8.1 Workload
Canonical source:
Audit_Obligations + Audit_Visit_Obligations + operational Audit planning projection.

Show:
- obligations/audits to plan;
- formal hours to plan;
- planned hours;
- unallocated workload;
- month;
- region;
- scope;
- auditor;
- planning window;
- status;
- lifecycle context.

8.2 Capacity
Primary operational source:
Auditor Availability.

Capacity is derived, not separately maintained as a second truth.

Inputs include:
- standard working-day convention;
- explicit Availability exceptions;
- hard unavailability;
- soft/default blocked days;
- occupied audit time;
- auditor default blocked weekdays.

Output per auditor:
- gross standard capacity;
- hard unavailable hours;
- soft unavailable hours;
- occupied audit hours;
- available capacity;
- overrideable soft capacity;
- assigned/planned workload;
- remaining headroom.

8.3 Planner View
Combine workload + capacity into one annual planning decision surface.

Important:
- distinguish Audit Obligations from unique physical Audit Visits;
- do not double-count bundled obligations;
- actual planned date must be available for month aggregation;
- workload and capacity must reconcile.

9. P1 — ROTATION PREASSIGNMENT WARNING

Never silently preassign an auditor with a rotation limitation.

Behaviour:
- visible warning before assignment;
- soft warning/waiver unless governance explicitly changes it to hard block;
- show current rotation count and threshold context;
- canonical rotation service remains owner;
- preferred surface: annual planner / Planning Workspace.

10. P1 — BATCH PLANNING

The earlier Concept Planning / Batch Planning work becomes a formal Planning 2.0 capability.

Flow:
- select multiple workload items;
- create concept batch;
- edit assignments/dates;
- run per-item validation;
- run whole-batch preflight;
- present committed / blocked / failed / already committed / skipped;
- explicit Apply.

Rules:
- no silent partial commit;
- no direct sheet writes;
- commit-time revalidation;
- batch ID / idempotency;
- concurrency protection;
- rollback/isolation strategy.

Later:
- bulk Re-adjust;
- move complete trip/week;
- replace auditor across selected audits;
- per-audit revalidation always retained.

11. P1 — TRIP & WORKWEEK PLANNING

Build on Planning 2.0 Concepts, not as a separate planning engine.

Flow:
1. choose period;
2. select region/workload;
3. choose feasible auditor;
4. select audits;
5. build concept trip/workweek;
6. sequence visits;
7. validate;
8. commit canonically.

Inputs:
- actual required locations;
- Companies.Locations_JSON;
- audit duration;
- planning windows;
- Availability;
- working-day limits;
- auditor base;
- company restrictions.

Travel modes:
- car;
- train where relevant;
- flight where relevant.

Compare:
- door-to-door time;
- feasibility;
- schedule impact;
- cost when reliable;
- sustainability burden.

Flight:
- explicit environmental penalty / soft score;
- never automatic hard block.

Hotel support:
- hotels visible in trip/map context;
- hotel can act as arrival/departure point;
- advisory only;
- no autonomous booking.

12. P2 — PLANNING INTELLIGENCE

Only after Planning 2.0 basic interaction is fast and stable.

Assignment advisory may use:
- qualification;
- region fit;
- continuity;
- travel burden;
- Availability fit;
- rotation pressure;
- workload/capacity.

Output:
- candidates;
- reasons;
- hard blocks;
- warnings;
- waiver context.

Manager remains decision owner.

13. PERFORMANCE TARGETS

All targets must be measured cold and warm and reviewed against real data size.

Initial targets:
- normal UI interaction should feel immediate where no server decision is required;
- common cached/read-model interactions target < 1 s;
- major decision-ready loads target approximately <= 2 s p95 where technically realistic;
- no normal user action should trigger repeated multi-second full-sheet scans;
- no regression accepted without measured explanation.

For every hot path log:
- total server time;
- major stage times;
- rows read;
- cache/read-model path;
- fallback path;
- build/version.

14. MIGRATION STRATEGY

Do not rewrite Planning 1.0 in one big-bang release.

Use progressive replacement:
1. measure current hot path;
2. establish reusable read model;
3. prove correctness;
4. switch one Planning 2.0 surface/action;
5. keep canonical writer unchanged;
6. regression test;
7. remove obsolete compatibility path only after proven replacement.

Planning 1.0 remains available during migration only where still required.

17. DEFINITION OF DONE — PLANNING 2.0

Planning 2.0 is not done because a new UI exists.

Done requires:
- Manager and Auditor use the shared planning architecture;
- Planning 1.0 slow hot paths are replaced or no longer user-critical;
- Availability Calendar is acceptably fast;
- Toolkit/Workspace is acceptably fast;
- no duplicate planning truth;
- all writes remain canonical;
- annual workload/capacity reconciles;
- rotation warning exists before risky preassignment;
- Re-adjust follows lifecycle governance;
- Batch Planning is canonical and safe;
- performance regression tests exist;
- operational errors are recoverable;
- DEV closure evidence is documented.
